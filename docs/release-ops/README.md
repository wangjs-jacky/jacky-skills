# Release OPS 分类与实现

更新日期：2026-10-15。读者：确认分类标准的用户，以及后续实现和维护发布经验的 Agent。

**状态：用户已于 2026-10-15 确认按发布平台分类。** [release-ops](../../harness/release-ops/SKILL.md) 已建立 4 个平台档案和 9 个 operations；三个旧发布 Skill 及其参考入口已改为共享知识路由。GitHub 推送和 PR 合并已有真实验证，其他操作仍为文档指导；安装、结构检查与执行证据在本机交付记录维护。

## 目标与首版范围

为反复使用的发布场景建立可持续维护的经验层：先命中对象和操作，读取适用事实，用当前配置复核，操作后自动写回证据。

首版覆盖 GitHub 仓库推送、PR 合并、GitHub Release、npm 包、VS Code Marketplace 和 Open VSX 扩展发布，以及这些链路的配置与排障。工作范围是用户当前需要的有限操作清单，不扩展成平台全部 API 手册。

服务部署、运行实例切换和移动端 OTA 继续由对应工程 OPS 管理；需要 GitHub Release 或 npm 分发时引用本 Skill。发布授权沿用当前任务，不由知识记录扩大。

## 一、已确认的分类

### 采用：`platform → operations`

| 平台 key | 归属 | 代表对象 |
| --- | --- | --- |
| `github` | 仓库、PR、tag、Release 的通用发布经验 | 仓库分支、PR、Release |
| `npm` | npm 包发布、认证适用条件、版本和 dist-tag 经验 | 指定 registry 中的包 |
| `vscode-marketplace` | VS Code Marketplace 的扩展发布经验 | publisher 下的扩展 |
| `open-vsx` | Open VSX 的扩展发布经验 | namespace 下的扩展 |

平台稳定 key 不含账号、项目或环境。GitHub Releases 是 GitHub 下的场景；Actions 是执行工作流的机制，不再为每种发布方式复制一套平台目录。CI 发布与本机发布通常是同一 operation 的条件分支，先核对项目实际采用哪种。

项目通过私有发布档案引用平台 operations。一个项目可以有多个包、扩展和分发目标；同一个版本发布到两个平台时，分别保留结果。平台规则只维护一份。

### 取舍记录：`project → operations`

适合主要任务是“维护某个工程从合并到上线的完整流程”。项目内可列发布 CLI、发布扩展、部署站点等操作；平台事实仍需要共享引用，以免各项目重复维护认证和限制。

用户已选择平台主键；项目保留流程映射。今后改变分类轴、拆并归属或扩大服务范围时再确认，当前日常经验按此标准自动维护。

## 二、首批 operations

以下场景已建立文档。各操作的当前可信度和实际验证日期，以 [平台索引](../../harness/release-ops/references/platforms/index.md) 下的平台档案和对应 operation 为准；不能将仓库推送、PR 合并成功外推为包或扩展已发布。

| 平台 | operation | 用户目标 | 成功所需证据 |
| --- | --- | --- | --- |
| GitHub | `publish-repository` | 首次把工程发布到仓库 | 目标仓库身份、可见性及指定分支提交符合要求 |
| GitHub | `push-changes` | 推送这次改动 | 目标 remote、分支与预期提交一致 |
| GitHub | `merge-pr` | 合并指定 PR | PR 处于已合并状态，目标分支包含对应合并结果 |
| GitHub | `publish-release` | 发布指定版本与附件 | tag 指向预期源码，Release 发布状态与指定附件对应 |
| npm | `configure-publishing` | 配置指定包的发布链路 | 工作流、触发条件、目标和认证模式可核对；首次真实发布是否验证单独记录 |
| npm | `publish-package` | 发布包的精确版本 | 精确 registry/包/版本可读回，所需 dist-tag 与产物信息匹配 |
| npm | `diagnose-publish-failure` | 定位发布失败并给出下一步 | 目标、执行记录、实际发布状态和根因证据能够对应；修复状态单独记录 |
| VS Code Marketplace | `publish-extension` | 发布指定扩展版本 | publisher、扩展、版本与发布结果对应 |
| Open VSX | `publish-extension` | 发布指定扩展版本 | namespace、扩展、版本与发布结果对应 |

扩展平台的首次配置和失败恢复先作为对应 operation 的分支；出现反复独立执行的需求时再拆操作。平台对“已接受”“公开可见”“可以下载”的具体状态语义，在实现时核对当前官方来源。

验证步骤属于各 operation 自身；如果用户反复只要求核实既有发布，再增加只读验证操作。首次配置可以完成配置目标，同时明确首次真实发布尚未验证。

## 三、知识与项目事实的归属

| 信息 | 唯一归属 |
| --- | --- |
| 平台边界、限制、认证机制及官方来源日期 | 平台 `index.md` |
| 用户目标、前置条件、分支流程、检查点、坑与恢复 | 对应 operation |
| 项目发布政策、版本文件、构建脚本和 CI 实现 | 项目现有指令、源码和 workflow；OPS 保存引用 |
| 工程身份、包/扩展与平台的映射、执行入口和实例证据 | ignored 私有项目档案，或已有工程 OPS 的同类档案 |
| 分类规则、候选操作和扩展策略 | `references/ops-model.md` |

已有工程 OPS 是项目发布信息的维护源时直接引用，不另建一份竞争档案。项目 workflow 或运行事实与旧经验不一致时，先核实差异，再修正记录。

私有项目档案最少记录：项目 key、当前源码位置的引用、发布目标表、版本来源、分支/tag/手动触发方式、工作流或脚本入口、认证模式及凭据来源名称、平台 operation 链接、最近证据与待办。单仓多包要逐个确认目标包与版本，不能仅凭仓库名选定发布对象。

凭据值不进入 Skill、全局指令或私有经验。发布记录保留核对身份所需的最小信息；项目专属规则不推广成平台通用规定。

## 四、每次任务的流程

1. 从实际安装位置读取入口和小型实例索引，明确本次目标及已有授权。
2. 命中项目发布档案或现有工程 OPS 的相关记录，仅定位本次发布对象。
3. 读平台索引、对应平台档案和 operation；仅跨目标任务补读其他平台。
4. 对照当前项目指令、相关 workflow、版本文件与运行证据复核历史记录，确认源码、版本、分发目标和触发方式。
5. 复用当前项目脚本或现有执行工具；实施授权范围内的操作。记录动作已经产生的结果，避免恢复时从头重复执行。
6. 按当前 operation 成功标准核对，写回对应知识和私有实例，说明已完成与未完成部分。

知识前置不会要求每次重新确认已授权的发布动作。CI 已通过、tag 已推送、registry 已出现版本分别证明不同结果；不能用其中一个替代整个任务的成功标准。检查、测试与试装按实际任务授权和所声明目标执行，不默认增加完整回归。

上传或网络报错导致结果不确定时，先核对目标当前状态，再决定能否恢复；不盲重发、自动升版本或覆盖已存在产物。恢复方式按具体平台与项目约束确定，不提供一条适用于所有平台的“通用回滚”。

## 五、自动沉淀

每次完成、失败或中断后自动判断并写回：

- 平台普遍适用的事实归平台档案，单个目标的方法和失败恢复归 operation，项目配置和执行记录归其私有实例。
- 区分 `documented`、`partial`、`verified`；成功日期只覆盖该 operation 声明且实际完成的目标。平台文档核对日期与执行验证日期分开。
- 多平台发布分别维护证据。一端成功、一端失败时，整体任务保持未完成，已完成端的结果仍保留，恢复只处理缺失部分。
- 重复成功刷新对应验证记录，正文有新事实才修改。迁移旧记录保留原日期，不把迁移日期当作真实成功日期。
- 发现旧规则失效时修正或降级，更新索引，保留必要历史依据；不只追加相互冲突的结论。
- 无新事实时如实说明；写入失败或校验未通过时报告未沉淀。

自动沉淀是 Agent 在本次任务内执行的工作协议，不创建后台监控，不自动提交、推送或再次发布。

## 六、与现有 Skills 的关系

| 现有内容 | 改造方向 |
| --- | --- |
| `github-repo-publish` | 保留用户入口；通用发布经验归 GitHub operations，npm/扩展内容归相应平台 |
| `npm-publish` | 保留用户入口；发布方式由项目配置决定，认证与平台经验集中维护 |
| `vsix-publish` | 保留用户入口；按实际平台区分发布与证据，通用打包实现继续复用工具和项目脚本 |
| `j-skills` 中的 CLI 发布说明 | 归属该 CLI 项目发布档案或已有工程 OPS，引用 npm operation；Skill 安装管理职责继续保留 |
| 已有工程 OPS，如 `happy-ops` | 继续负责工程上下文和项目流程；引用共享发布经验，保存自己的实例证据 |

旧入口可逐步缩为路由与必要执行说明。知识迁移时同步修正原规则和链接，避免新旧两套规范竞争；`release-ops` 不再反向依赖旧入口来获取同一份知识。具体实现仍调用现有 CLI、项目脚本或实际执行 Skill。

源码保持独立，引用到目标 OPS 时按当前安装注册表或技能目录定位，不要求目录相邻。浏览器操作读取 `ego-ops`；涉及 Cloudflare 时读取 `cloudflare-ops` 并遵守禁止轮询约束。知识只写回各自归属。

首版采用 Markdown 协议与路由，不为发布流程新增自动执行服务。脚本只在重复、确定性需求明确时增加。

## 八、安装 Agent 的全局前置提示词

完整提示词的唯一维护源为 [release-ops 安装提示词](../../harness/release-ops/references/global-agents-prompt.md)，入口顶部已提供链接。安装 Agent 展示完整规则、实际全局文件与生效范围，用户同意后才合并；普通使用不重复询问。文件复制不会自动执行交互，全局规则也不是执行器拦截钩子。

本次生成提示词，不将分类确认等同于全局配置授权。
