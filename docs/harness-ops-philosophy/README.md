# Harness 与 Ops 设计理念

从 Worktree 碎片到持续进化的工程经验层

**文档类型**：设计理念与仓库规范说明

**适用范围**：自有工程、工具链与复杂第三方 Skills

**核心结构**：`harness/<target>-ops/`

**更新日期**：2026-07-11

## 核心判断

Harness 不是另一个文档文件夹，而是一套让 AI 先读经验、验证现实、解决问题并写回新经验的稳定协议；Ops 是这套协议面向某个具体工程或工具的运行实例。

这套设计要解决的不是"文档放在哪里"这么简单的问题，而是工程经验如何在不同会话、不同 Worktree、不同版本和不同 Agent 之间持续存在，并且始终能被当前真实运行态校正。

## Harness 与 Ops，各自负责什么

Harness 是架构名。它强调"驾驭层"：在能力之外增加读取、路由、验证、写回和持续进化的约束。Ops 是实例名，是 Operations 的缩写，表示围绕一个目标对象的运行、维护、调试、适配和复盘。

| 概念 | 职责 | 典型内容 |
|------|------|----------|
| `harness/` | 仓库级分类与稳定协议 | 创建规则、命名规则、经验分层和写回循环 |
| `<target>-ops` | 面向具体对象的可触发 Skill | 问题路由、最佳实践、兼容性和复盘方法 |
| `SKILL.md` | 可分享、可版本化的通用层 | 触发条件、稳定流程、隐私边界和泛化结论 |
| `experience.local.md` | 本机实时事实层 | 路径、代理、拓扑、版本、错误、修复和验证证据 |

## 为什么不能只写 CLAUDE.md

CLAUDE.md 适合保存工程内、需要随代码版本化的稳定约定，但不适合承担持续变化的本机运行经验。尤其在频繁使用 Worktree 时，同一个工程会出现多个目录，每个目录都可能拥有不同版本的 CLAUDE.md：

- **经验跟随分支复制**：同一个问题可能在多个 Worktree 重复排查。
- **本机事实难以版本化**：路径、代理、登录态和机器拓扑不应进入公开 Git。
- **合并成本高**：一次本地修复经验可能需要跨分支同步，容易遗漏或产生冲突。
- **事实容易过期**：版本库里的旧结论可能继续被 Agent 当作当前运行态。

**设计取舍**：业务工程的 CLAUDE.md 继续管理"这个版本的代码应该怎样协作"；外部 Ops Skill 管理"这套工程在我的环境中怎样长期运行和维护"。

## 独立经验层解决 Worktree 分叉

Ops Skill 放在独立的 `jacky-skills/harness/` 中，不随被维护工程的 Worktree 复制。多个 Worktree 调用同一个已链接的 Ops Skill，读取同一份 experience.local.md；问题只需验证一次，后续会话即可复用。

```
多个 Worktree             同一个 <target>-ops          一个本机经验源
代码和 CLAUDE.md 可以不同 → 统一路由、验证和写回协议 → 保存最近核实的真实结论
```

## 第三方 Skills 也需要 Ops

复杂的第三方 Skill 通常只描述通用能力和理想环境。它可能有官方推荐组合、隐含前置条件和版本耦合，也可能在某台电脑上因网络、代理、浏览器、字体、缓存或运行时版本而"水土不服"。这些问题既不应该反复从零排查，也不应该直接写回或修改上游 Skill。

| 层 | 应该负责 | 不应该负责 |
|----|----------|------------|
| 官方 Skill | 通用能力、官方工作流和版本化分发 | 用户私有路径、代理和单机故障历史 |
| 配套 Ops Skill | 最佳实践、能力组合、兼容差异和已验证绕法 | 复制上游全部内容或长期维护私有分叉 |
| 本地经验文件 | 当前机器事实和带日期的复盘证据 | 未经验证就推广为通用规则 |

## 第三方适配层：HyperFrames 历史例子

HyperFrames 官方 Skills 负责视频创作、动画、渲染和工作流能力。现已移除的 `hyperframes-ops` 曾用于积累以下本机适配知识；当前创作与排障直接按官方 Skills 和运行证据处理，本节仅保留设计背景：

- **最佳实践**：官方多个 Skills 应按什么顺序组合，什么时候使用哪一层能力。
- **水土不服**：Node、FFmpeg、浏览器、字体下载、代理和 OAuth 登录态造成的本机错误。
- **版本差异**：官方命令、manifest、安装器或清理语义变化后，旧经验是否仍有效。
- **已验证绕法**：具体修复动作、验证命令和最近核实日期。

**不修改上游**：官方 Skills 保持可更新；本机差异留在 ops。上游升级后先重新验证，旧经验失效就明确标记或替换。

## 经验写回规则

| 发现 | 写入位置 | 判断标准 |
|------|----------|----------|
| 本机路径、代理、端口、机器或账号 | `experience.local.md` | 包含个人环境事实，不进入 Git |
| 一次错误的现象、根因、处理和验证 | `experience.local.md` | 先作为带日期的本机复盘保存 |
| 第三方 Skill 的本机兼容问题 | `experience.local.md` | 可能随机器和上游版本变化 |
| 反复验证的通用最佳实践 | `SKILL.md` | 换一台机器仍成立，并能减少未来试错 |
| 详细但可分享的机制说明 | `references/` | 不应挤占 SKILL.md 的核心上下文 |
| 确定性、反复执行的修复动作 | `scripts/` | 脚本比每次临时重写更可靠 |

## 实时更新不是无条件追加

Ops Skill 需要在真实使用中及时更新，但"实时"不等于把所有猜测都写进去。写回必须发生在已有验证证据之后，并且要维护唯一、可判断的新旧关系：

1. 进入 Skill 后先读取本地经验，定位已有结论和最近验证时间。
2. 检查源码、日志或运行态，验证会漂移的事实。
3. 完成修复或最佳实践验证，保留最小可复现步骤和验收证据。
4. 当场写回 `experience.local.md`；若旧结论失效，直接标记或替换。
5. 只有跨环境仍成立的知识，才提炼进 `SKILL.md` 或 `references/`。

## 标准目录和创建规则

创建 harness skill 时，默认结构：

```
harness/<target>-ops/
├── SKILL.md
├── .gitignore
└── experience.local.md
```

- 目录名与 frontmatter `name` 必须一致，并以 `-ops` 结尾。
- 不再创建 `*-harness`；`harness` 只作为顶层分类。
- 使用官方 `skill-creator` 创建或更新 Skill。
- 只有真实需要时才增加 `scripts/`、`references/` 或 `assets/`。
- 设计理念和用户文档统一放在 `docs/`，不塞进单个 Skill。

## 收敛结果

| 原位置 | 新位置 | 定位 |
|--------|--------|------|
| `skills/happy-ops` | `harness/happy-ops` | 自有工程运行与拓扑经验 |
| `skills/opencli-harness` | `harness/opencli-ops`（已移除） | 历史：工具使用配方与 adapter 缺口经验 |
| `skills/hyperframes-harness` | `harness/hyperframes-ops`（已移除） | 历史：第三方 Skills 最佳实践与本机适配 |

名称中包含 `harness` 但职责是评测、打分或基准测试的 Skill 不迁入本目录。例如 `harness-benchmark` 属于评测工具，而不是某个目标对象的 Ops 经验层。

## 完成标准

- 新的 harness skill 能被稳定路由到 `harness/<target>-ops/`。
- 所有 Ops Skills 都能在工作前读取本地经验，在验证后写回。
- 本机私有事实不会进入 Git，可分享内容不依赖个人路径或秘密。
- 业务工程的多个 Worktree 不再各自维护一份重复经验。
- 第三方 Skills 可以继续升级，本机适配经验不会被覆盖或丢失。
- 旧经验与当前运行态冲突时，以最近验证证据为准。

> 稳定的是协议，持续生长的是能力。
