# 正式构建的通用取舍

> 面向“要产出可对外分发的正式包”这一目标的跨技术栈思路骨架。具体命令、profile 名和渠道配置由目标仓库现场决定，本机私有值只留在被忽略的 `local/`。

## 什么时候进入正式构建

- 产物要走真机验收、内测分发、商店审核或正式 Release，而不只是本地跑通。
- 涉及原生依赖、权限、包标识、runtime、更新端点变化——这类改动无法用 OTA 覆盖，必须重新构建。
- 需要一个可追溯、可复现、可回滚的稳定基线。

## 构建前必须核对

1. **版本与标识**：对外版本号、内部构建号（versionCode / build number）是否按渠道单调递增；包标识（bundle id / applicationId）是否与目标渠道一致。
2. **runtime 与兼容边界**：runtime version、最低系统版本、ABI/架构是否覆盖目标设备；原生依赖图是否与将要发布的更新通道兼容。
3. **签名与凭据**：签名身份、证书/描述文件、密钥来源是否正确且未过期；凭据只从专门的凭据系统取，绝不写进仓库或 `references/`。
4. **构建 profile 分层**：development / preview / production 使用独立 profile 与独立更新通道，避免正式产物误连开发通道。
5. **权限与配置**：权限声明、第三方 key、环境区分（测试/生产端点）是否与正式渠道匹配。

## 可复现与产物核对

- 构建应尽量可复现：固定依赖版本、锁定工具链、记录构建输入，便于同一提交重复产出一致产物。
- 构建完成后核对产物指纹（大小、签名、版本、包标识）与预期一致，再进入下一步；不要用“构建成功”本身当作产物正确的证据。
- 保留构建输入与关键日志到被忽略的 `local/runs/`，作为回滚和复盘证据，而不是塞进上下文或提交进 Git。

## 边界

- 正式构建成功只证明“能产出这个包”，不证明 UX、真机行为或验收通过；真机与人工验收是后续独立步骤。
- 本能力负责产出可验证的构建，不负责决定何时对外发布——发布授权与渠道核对属于 `app-flow-delivery`。
- 迁移到新项目时重新确认版本策略、签名体系、runtime 与原生依赖，不照抄任何具体数字或命令。
