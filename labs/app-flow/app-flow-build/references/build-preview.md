# 预览 / 开发构建的通用取舍

> 面向“要快速验证、内部试用、不对外正式发布”这一目标的跨技术栈思路骨架。具体命令、profile 名和分发工具由目标仓库现场决定。

## 什么时候用预览构建

- 需要在真机或内部人员手里验证交互、手势、触感、系统权限等本地/CI 观察不到的行为。
- 一个改动能通过静态检查和自动化测试，但还需要真机确认才能进入正式流程。
- 想给内测者、评审者或产品一个可安装的候选，而不占用正式版本号。

## 预览构建的原则

1. **走独立 profile 与通道**：预览用独立构建 profile 和独立更新/分发通道，绝不与生产通道混用，避免内测产物流入正式用户。
2. **先过可自动化的检查**：预览构建不替代 typecheck、lint、单测和结构化回归；这些能在本地或 CI 证明的检查应在打预览包之前完成。
3. **标注清楚是预览**：版本命名或渠道标识要能一眼区分预览与正式，避免误当正式产物验收或分发。
4. **迭代要快、要可丢弃**：预览产物是过程物，允许频繁重打；证据留在被忽略的 `local/`，不需要长期保存每个预览包。

## 与 OTA 的关系

- 若项目支持 JS 层热更新（OTA），只有 JavaScript 兼容的改动适合走预览 OTA；涉及原生变化仍需重新出预览构建。
- 预览 OTA 与预览构建都不是最终确认，真机验收和正式发布授权是后续独立步骤，属于 `app-flow-delivery`。

## 边界

- 预览构建只服务“快速看到效果”，不产出可对外正式分发的包；正式产出见 [`build-production.md`](build-production.md)。
- 迁移到新项目时重新确认预览 profile、分发方式和内测通道，不照抄具体配置。
