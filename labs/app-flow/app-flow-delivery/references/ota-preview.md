# 预览 OTA 的通用边界

> 面向支持 JS 层热更新（OTA）的 App，把“给内测者下发预览更新”这一动作的通用取舍抽成骨架。具体命令与通道由目标仓库现场决定。

## 什么时候用预览 OTA

- 一个 JS 兼容改动需要在内测者真机上快速验证交互、手势、系统行为，而不必重打正式包。
- 想让评审者或产品在不影响线上用户的前提下试用候选。

## 预览 OTA 的原则

1. **独立预览通道**：只下发到预览/内测通道，绝不混入正式通道。
2. **先过可自动化检查**：预览 OTA 不替代 typecheck、单测和结构化回归；能在本地或 CI 证明的检查应在下发前完成——预览 OTA 曾被误当作主要 QA，应避免重演。
3. **runtime 对齐**：预览 OTA 声明的 runtime 与内测二进制一致，否则内测设备拉不到。
4. **可丢弃**：预览 OTA 是过程物，允许频繁下发；证据留在被忽略的 `local/`，不长期保存每次下发。

## 顺序不能省

保留发布顺序：**静态检查与自动化回归 → 预览构建或预览 OTA → 真机最终确认 → 获得授权后正式发布**。预览 OTA 处在中段，既不是起点也不是终点。

## 边界

- 涉及原生变化时预览 OTA 无效，需重新出预览构建。
- 预览 OTA 不是发布授权；正式下发见 [`ota-production.md`](ota-production.md)。
- 迁移到新项目时重新确认预览通道与 runtime，不照抄具体配置。
