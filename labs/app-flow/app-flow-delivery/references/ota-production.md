# 正式 OTA 的通用边界

> 面向支持 JS 层热更新（OTA）的 App，把“正式向线上用户下发更新”这一动作的通用取舍抽成骨架。具体命令、通道名和端点由目标仓库现场决定，本机私有值只留在被忽略的 `local/`。

## OTA 只覆盖 JS 兼容改动

- 只有 JavaScript / 资源层、且与当前线上二进制兼容的改动适合走 OTA。
- 涉及原生依赖、新增或变更原生权限、原生插件、包标识、更新 URL 或 runtime version 的变化，**必须重新构建 App**，不能用一次成功的 OTA 导出证明原生仍兼容。
- 权限若已在当前二进制声明，只是 JS 交互或文案变化，按实际 native diff 判断，不因为出现“权限”二字就一概重建。

## 正式下发前核对

1. **runtime 匹配**：OTA 包声明的 runtime version 与线上二进制一致，否则设备拉不到或崩溃。
2. **通道正确**：下发到正式通道而非预览/开发通道；通道与目标用户群一致。
3. **授权确认**：正式 OTA 是对线上可见的外部动作，必须重新确认用户对“这个通道、这次下发”的明确授权。
4. **回滚就绪**：能快速回滚到上一可用 OTA 或提示用户回退；回滚路径已验证。
5. **验活方式**：下发后如何确认真实生效（版本号、关键路径），而不是只看发布命令返回成功。

## 边界

- 正式 OTA 不替代 typecheck、自动化测试和结构化回归；这些应在下发前完成。
- 真机与人工验收验证的是机器观察不到的最后一层，不负责发现基础结构错误。
- 迁移到新项目时重新确认更新运行时、原生依赖图、权限、插件、包标识和更新端点；任一项跨过现有二进制兼容边界，就选新构建而不是 OTA。预览通道见 [`ota-preview.md`](ota-preview.md)。
