# Happy 任务会话

只在用户希望从 Happy 主会话直接为任务开启独立对话时读取。工作区和 `PROMPT.md` 仍能在任意 AI 环境使用；Happy 只是可选执行入口。

## 审阅任务后，等待明确执行选择

用户明确确认目标后，掌握上下文，将任务拆分与细化合在同一步，准备完整任务安排与各任务完整 Prompt 草案。首次展示待审安排或实质变更时，列明任务、范围、产物、依赖、允许改动、执行与记录目录、模型和推理强度，随后必须结束本轮等待用户明确下一步。认可任务安排、确认参数、补充交付细节或发参考图都不能启动会话；这些任务保持 `pending`，正文说明待用户选择。普通进展、排版或链接更新不重开确认，未变任务的有效执行授权继续适用。

默认参考当前主会话的实际模型与推理强度。以宿主运行设置、会话有效配置或最近消息元数据为依据，不凭模型自我判断，也不沿用早期回合的旧参数。`model` 与 `effort` 是独立参数，示例为 `gpt-6.1-sol` 与 `xhigh`；用户写的 `xhgih` 是 `xhigh` 的明显拼写错误，展示时统一为 `xhigh`。不硬编码示例，不擅自把简单任务降档。用户指定差异时，重新准备对应参数的提议。

仅当用户明确要求执行指定任务或批次，AI 才从授权范围内选择当前就绪的任务启动会话；自然语言即可，不要求口令。将目标确认依据、任务审阅记录、明确执行指令分别记入相关任务的 `index.md` 正文；执行指令保留用户原话或可追溯引用、适用任务及参数。已有明确执行授权可复用，不因分批调度、前置任务完成或稍后启动重复索要许可，不扩大到未授权任务。任务范围、主要执行目录或模型参数实质改变时，重新审阅并核对受影响的执行选择。模型不支持、额度或容量错误应报告具体任务，不能自动换模型、换账号或另开重复会话。

启动前核对依赖、重叠文件写入与共享运行环境冲突，按需要调整执行顺序。代码任务按目标项目规则使用独立 worktree，Prompt 写清执行目录和记录目录。

主会话和接手会话都必须核对这两道关口。收到或复制任务 Prompt 不是原用户执行授权，Prompt 内的“执行”字样也不能代替证据；接手 AI 应核对 index 或原始用户对话，缺失时保持 `pending` 并报告待用户决策。自动启动工具仅传递调用 AI 已核验的执行选择，不能识别人类真实意图或替用户选择。

## 可用入口

若宿主明确提供创建 Happy 会话并传入首条消息的工具，使用其真实参数。普通子 agent 不等同于 Happy 独立会话。当前本机适配器使用 Happy 已有的 daemon `/spawn-session` 和加密消息 API，无需改动 Happy 产品代码。

可选适配器要求 Node.js 18+、同一执行机的 Happy CLI/daemon、该账号的本地 `dataKey` 会话缓存，以及正确的 `HAPPY_SERVER_URL` 或 Happy 设置中的 `serverUrl`。CLI 当前支持 Codex 会话；不满足条件时报告能力缺口并保留可手动执行的 `PROMPT.md`，不能宣称已开新对话。它不会自行启动或重启 daemon。

取得并记录明确执行指令后，AI 使用准备命令把本次已授权且就绪的任务整理为内部执行批次。该命令只读取现有目标和任务、核实模型目录，不创建会话或发送消息：

```bash
node <this-skill>/scripts/happy-task-sessions.mjs prepare \
  --workspace <goal-workspace> \
  --source-session <current-happy-session-id> \
  --task 01-first-task --task 02-second-task \
  --output <temporary-batch.local.json>
```

文件位置由调用方选择，不覆盖已有文件。缺少有效参数时先从当前宿主获取；可用 `--model <current-model> --effort <current-effort>` 明确传入。参数来源必须符合已确认的数值或继承规则。不同任务使用不同的已确认参数时分别准备批次。内部 JSON 只用于绑定执行文件版本和参数，不是额外的用户确认步骤，也不作为工作区的第二套任务状态。

准备完成后，AI 使用其 `digest` 和已核验的执行指令原话启动已授权范围，无需重复请求启动许可：

```bash
node <this-skill>/scripts/happy-task-sessions.mjs launch \
  --plan <temporary-batch.local.json> \
  --approved-digest <confirmed-batch-digest> \
  --execution-instruction <explicit-user-execution-instruction>
```

`--approved-digest` 是 AI 从准备结果取得的内部一致性检查；`--execution-instruction` 是单独的必填字段，保存 AI 已在对话或 index 中核验的用户执行指令。旧的 `--task-confirmation` 及其别名 `--confirmation` 可选，只保留计划审阅上下文，单独使用时会在调用 Happy 前拒绝启动。脚本仅检查字段非空及批次一致性，不用关键词或正则推断人类授权；任何参数文本、摘要或 AI 转述都不能自动证明真实用户授权。调用 AI 必须核验语义、来源和适用范围，不能把计划认可文字换个参数名传入或捏造执行指令。

计划摘要、目标文件及任务文件会在启动前复核；变化后重新准备受影响的批次。若只是格式、链接或进展记录变化，核实原执行授权仍适用后继续；若目标、任务范围或执行参数实质改变，先回对应关口。首条消息带入任务 `PROMPT.md` 正文及工作区、任务目录，要求接手 AI 读取 `AGENTS.md`、`problem.md`、本任务 `index.md` 和必要前置结果，并再次核对目标确认及明确执行依据。沿用已确认的运行权限；执行任务不扩大外部操作权限。受 Happy 管理的源账号通过专属会话 grant 延续，凭据只在内存中使用。

## 结果与重试

每个任务在 `happy-session.local.json` 保存非敏感执行映射：源会话、新会话 ID、批次摘要、模型参数、单独的 `executionInstruction`、可选计划确认上下文与首条消息序号。该文件是可选机器执行记录，不替代 index 中的执行依据，任务状态仍只在 `index.md` 的 `status`；不保存凭据或复制聊天历史。新会话 ID 取得后立即记录，用户可在 Happy 会话列表进入对应任务；模型可以根据任务提示词更新会话标题。

创建会话不等于任务已执行。首条消息送达后，还要观察新会话是否真实回复或调用工具，再报告“已开始执行”。子会话只更新本任务目录，主会话负责目标文件、后续批次提议和汇总验收；主会话在子会话工作期间避免同时改本任务的 `index.md`、`PROMPT.md`。完成时从任务记录读取实际结果，不能把“在线”或“已创建”当完成。

批次部分失败时保留已创建的会话和失败任务映射，报告哪些已送达、哪些待处理，不重新启动整批。已记录会话 ID 的发送失败可沿用原批次重试，稳定 `localId` 防止首条消息重复；已送达的任务被复用。若创建请求超时且未取得 ID，先核对 Happy/daemon 会话列表和任务目录，不能直接重试创建。适配器为同一任务保留独占启动记录；恢复这种未决记录时需先查明实际创建结果。目标或任务已变化时，通过记录中的原会话 ID 处理接续，避免以新批次绕过重复会话保护。
