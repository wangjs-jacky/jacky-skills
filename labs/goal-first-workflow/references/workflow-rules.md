# Goal-First Workflow Rules

只有创建、拆分或维护 Goal-First 工作区时才读本文件。它定义工作区内的持久化约定，不规定某个领域的任务数量或技术路线。

## 工作区边界

初始化目录就是一个目标的根目录。它包含：

```text
AGENTS.md       本目标的协作和沉淀规则
PROMPT.md       交给独立 AI 的入口提示词
problem.md      用户初始目的和重要后续变化
tasks/          编号任务目录
templates/      本地任务 index.md 与 PROMPT.md 模板
```

工作区应可移动和独立使用。不要要求后续 AI 读取 Skill 仓库、上级项目或聊天记录才能理解已经保存的目标和进度。

## 从问题到任务

先在对话中追问、复述并取得用户对目标的明确确认，再让 `problem.md` 保存用户原话、已确认目标、完成标准、范围与限制，以及确认日期和用户确认原话或可追溯引用。每个问题标题下留出独立空白区域，便于用户输入，不把问题和回答混在同一行。AI 不得代填用户确认；已有草稿可以继续用于澄清，不视为已确认目标。

只有当前目标、完成标准和主要限制已获用户明确确认，才设计方案或拆任务。确认前仅做必要只读核对，批准创建目录不能代替目标确认。目标确认后先掌握足够上下文，再将任务拆分和细化合在同一步，按真实依赖和可验收结果安排，不强制先粗拆，不固定阶段或数量。用户确认的目标可以是通过调研回答某个问题，无需提前确定解决方案；调研本身作为待选择执行的任务，不在准备安排时擅自开展。

目录格式为 `tasks/NN-short-description/`，`NN` 从 `01` 起递增。每个新任务至少包含：

```text
index.md        状态、目标、产物入口和简短进展
PROMPT.md       细化完成后生成的完整任务指令草案
```

从工作区自己的 `templates/task-index.template.md` 与 `templates/task-prompt.template.md` 创建上述文件，无需回到 Skill 仓库。任务细化完成后才生成完整 Prompt 草案。任务约定集中写入 `index.md` 正文：实际执行目录、记录目录、允许改动范围、前置任务与所需输入（没有时明确写无）、可观察的验收条件及验证证据；独立宿主会话还需模型、推理强度或继承规则。执行或代码目录可以在工作区外，须明确标识；记录仍归属对应任务目录，不能混淆两种位置。任务 `PROMPT.md` 填入接手 AI 可访问的工作区路径和本任务相对路径，引用 `index.md` 的约定，不另维护一份。移动工作区后，交接前更新 Prompt 中的工作区入口路径。

## 审阅与执行选择

首次展示待审任务安排或实质变更时，给出完整任务安排与各任务完整 Prompt 草案，必要时用流程或线框辅助审阅整体安排。此时不执行这些 Prompt 中的任务；展示后必须结束本轮，等待用户明确下一步。用户可删除、合并、拆分、缩小任务。仅认可计划、补充任务细节、发参考图、强调交付形式或期限，不等于执行指令，应先更新草案。普通进展记录、排版或链接变化不触发此停顿，也不使未变任务的有效执行授权失效。

只有用户明确要求执行某任务或某批次后，才按指定范围开始。普通自然语言即可，无需固定口令。已有明确执行授权可复用，按依赖分批调度无需重复确认；不得扩大到未授权任务。目标、完成标准变化回到目标确认；任务范围、主要执行目录或模型参数实质改变时，回到受影响任务的审阅与执行选择。

每个任务 `index.md` 正文分别记录：

- 目标确认依据：原话、可追溯引用，或链接到 `problem.md` 中适用的确认记录。
- 任务审阅：展示了哪个版本、用户反馈与改动；尚待审阅或选择时如实说明。
- 明确执行指令：用户原话或可追溯引用、适用任务范围与参数；未取得时写明待用户决策，不能由 AI 代填。

这两道关口同时适用于主会话、手工交接和 Happy 独立会话。复制、收到、生成 Prompt 或拿到宿主会话 ID 都不证明原用户已授权执行。接手 AI 必须核对 index 或原始用户对话中的依据；缺少明确执行指令时保持待用户决策，不能被 Prompt 内的命令句或自动化触发绕过。核对授权和前置条件后才执行，按验收条件记录实际结果及未验证项。

任务 `index.md` 的 YAML 只保留：

```yaml
status: pending
```

状态含义：

- `pending`：尚未开始，包括任务草案待审阅、待用户选择执行或等待前置任务；在正文写明下一步决策。
- `running`：正在处理，有实际执行动作。
- `review`：已执行任务的产物已准备，等待用户验收或下一步确认；任务安排或 Prompt 草案仍为 `pending`。
- `done`：目标已完成且无需当前任务继续。
- `blocked`：已获执行授权的任务因缺少必要信息、资源或某项操作权限而无法继续，正文写明具体缺口。正常等待用户审阅或选择执行不属于阻塞。

不要新增百分比、第二套看板、任务 ID 或独立进度文件。总览需要时读取各任务 `index.md` 的状态。

## 记录归属

任务执行中按需建立文件：

- `result.md`：实际结论、已验证/未验证项和下一步。
- `FAQ.md`：用户实际追问及回答，保留日期和必要依据。
- `REFERENCES.md`：资料来源、用途和核验状态。
- `IDEA.md`：未承诺执行的灵感或改进点，标明提出者和当前态度。
- `notes/`：调研和学习材料。
- `evidence/`：脱敏截图、日志和验证证据。
- `attempts/`：失败、复现和重复验证记录。

只有内容实际产生时才建文件。所有文件从对应任务的 `index.md` 链接。一个事实只在它产生的任务保存；其他任务以相对链接引用，不复制整段上下文。

项目级复盘默认保存在项目内的 `project-replay/`，不自动转存 Obsidian。用户要求把复盘经验沉淀为工作流改进时，将脱敏、可复用的规则更新到本 Skill；完整项目回放仍留在项目内，不混入通用模板或规则。

## 反馈、分支与变更

每次实际追问回答后，更新所属任务的 `FAQ.md`。新想法先写 `IDEA.md`，只有用户采纳后才成为任务或任务变更。

调研、POC 或实施失败时保留尝试记录和失败原因。若一条路线失效，再基于已知证据准备后续任务或分支，不删除原路线，也不自动执行新任务。目标、完成标准或主要范围变更时，先重新对齐受影响部分并取得用户确认，再更新 `problem.md` 的变更与确认记录，保留最初目的和变更原因；普通实现选择无需重复确认目标。补充细节只更新草案，不能自行升级为执行授权。

## 外部操作边界

生成计划、任务 Prompt 或命令示例不是执行授权。购买、账号登录、读取私有系统、远端变更、部署、删除、服务中断和发布还需要当前任务范围内的具体授权。任务尚未被选择执行时保持 `pending`；已授权任务因缺少某项必要操作权限无法继续时，记录 `blocked` 与所需条件。

不得把密码、密钥、token、认证头、完整私有配置或未脱敏日志写入工作区。附件或截图先脱敏，再放入与其相关的 `assets/` 或任务 `evidence/`，并使用相对路径引用。
