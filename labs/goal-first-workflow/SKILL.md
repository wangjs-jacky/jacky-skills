# Goal-First Workflow

把一个用户目标变成独立、可持续推进的文件化工作区。它保留原始目的，按实际需要拆分任务，并让每项结果都有归属和可追溯记录。

## 何时使用

适用于用户要开启一个新需求、将模糊目标整理成可执行任务、为一个项目建立状态和证据记录，或需要让多个独立 AI 能接续工作。

不用于只回答一个问题、执行已存在的单一任务、替代项目已有工作流，或把一份技术方案直接当作所有任务的授权。

## 开始前

创建或维护工作区前，阅读 [workflow rules](references/workflow-rules.md)。规则定义目录归属、状态含义、任务沉淀和外部操作边界。

当用户同意创建一个新的工作区后，运行：

```bash
node <this-skill>/scripts/init-goal-project.mjs <destination-directory>
```

初始化器只接受一个目标目录；它不会覆盖非空目录、创建任务、调用网络、变更 Git，或代表用户选择目标位置。

## 工作流

1. 请用户填写或共同整理新工作区的 `problem.md`。先确认目标、完成标准、现有材料、限制和人脑中的关键上下文；不要急着生成技术方案。
2. 读取工作区 `AGENTS.md` 和 `problem.md`。目标已足够明确时，按实际工作边界创建必要的 `tasks/NN-short-description/` 目录；每个任务从 `assets/project-template/task-index.template.md` 和 `task-prompt.template.md` 创建 `index.md`、`PROMPT.md`。
3. 每个任务只维护一个 YAML `status`：`pending`、`running`、`review`、`done` 或 `blocked`。先读指定任务及必需前置结果，只推进当前被指定的任务。
4. 把实际结果、依据、失败、用户追问和新想法写回产生它们的任务目录，并从该任务 `index.md` 链接。反馈改变目标或路线时，保留原始目的与变更原因。
5. 遇到付款、账号、远端修改、发布、删除或中断服务等外部动作时，核对具体授权；缺少授权或必要输入就记录 `blocked`，不要猜测或绕过。

## 结果标准

一个健康的工作区让另一位 AI 仅靠本目录就能知道：用户最初想达成什么、当前任务是什么、已经实际完成了什么、证据在哪里、为什么下一步存在或被阻塞。

模板和规则必须保持领域中性。不要把某次项目的服务器、凭据、供应商、协议、绝对路径或私人案例写进本 Skill 或生成的工作区。
