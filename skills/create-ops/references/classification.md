# 分类设计：先确定知识归属

创建或改变分类规则时读取。人参与决定“经验放在哪里”；Agent 根据已确认规则维护具体经验。

## 选择一个稳定主键

| 场景 | 可推荐的分类轴 | key 示例 | operation 示例，仅作需求候选 |
| --- | --- | --- | --- |
| 浏览器自动化 | `site` | `bilibili` | 收藏视频、下载视频、点赞、发表评论 |
| Cloudflare | `capability` / `feature` | `workers`、`durable-objects` | 发布并验证、设计状态服务、诊断读额度 |
| 工程运维 | 由实际职责确定的 `system` | `web`、`server` | 部署、回滚、诊断启动失败 |

`site + operations` 与 `feature + operations` 使用同一组织方法，差别是分类轴。`feature` 与 `capability` 若在当前领域同义，就选一个名称并记录别名，避免建两套重复目录。

判断一个主键是否适合：

- 用户描述任务时是否很容易命中它。
- 域名别名、账号、环境、版本或一次任务变化时，能否继续复用相同知识。
- 同一 key 下是否存在多个 operation 共用的事实和限制。
- 一条经验能否找到清楚的唯一归属。

同一站点的多个域名通常是别名；同一能力的开发与生产环境通常是实例。若用户确实按项目维护工程，项目也可以是稳定主键，不机械禁止。跨对象工作指定一个拥有总体目标的 operation，引用其他对象的事实，不生成 `site × feature × environment` 全组合目录。

## operation 的粒度

按用户能说清的目标拆分：收藏视频、发表评论、部署并验证。点击按钮、读取 DOM、调用 API 属于执行步骤。不同工具能完成同一目标时通常共用 operation；工具版本差异写适用条件。

成功标准或授权边界明显不同的目标应拆分。例如“读取评论”和“发表评论”不是同一个 operation。“诊断超限”成功，也不代表“修复超限”成功。

常用操作是**当前服务范围内可以列清楚的有限集合**，不要求枚举产品所有功能。尚未执行的用户需求可以进入候选清单；领域允许设计知识时可标为 `documented`，禁止填写虚构步骤和验证日期。

## 给用户看的具体方案

先给推荐方案，只有存在真实分歧才给备选。可以这样组织：

> 建议按 site 分类；同一站点的域名和环境作为别名或实例。Bilibili 的首批操作为你要用的收藏、下载、点赞、评论。平时按这个分类自动沉淀；改变分类标准或扩大服务范围时再确认。

询问重点是主键是否正确、常用操作是否覆盖需求、扩展边界是否符合偏好。用户已明确回答的部分直接记录，不要求机械填写表格。没有确认的方案标记为“待确认”，不能写成已批准。

## 何时再次邀请人参与

- 现有主键不能解释新的任务，准备新增维度或改变分类轴。
- 准备合并、拆分或重命名既有归属，影响已有引用和使用习惯。
- 任务超出已确认服务范围。
- 用户选择了更严格的新增 key/operation 确认策略。

在已确认范围内更新证据、修正过期步骤、增加同类操作和别名，按记录的策略自动完成。一次新经验不应自动触发全库重构。
