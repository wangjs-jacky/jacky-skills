# Create OPS

把用户反复做的少量事情组织为 **稳定分类主键 → operations**，让每次真实工作都能复用和修正经验。分类由人参与决定，执行和经验维护由 Agent 承担。

## 先确定本次工作

- **新建**：明确服务对象、实际场景和可用执行工具，创建 `<target>-ops`。
- **改造**：保留现有能力、授权边界与证据，把散落经验归入稳定分类和 operations。先读[创建与迁移](references/creation-and-migration.md)。
- **补齐机制**：已有分类可复用时，直接补自动沉淀、索引或安装提示词，不重新设计整库。
- 普通业务操作交给对应 OPS；不要每次执行都重新进入创建流程。

使用当前环境提供的官方 `skill-creator` 完成 Skill 结构与元数据工作；按目录或安装注册表定位，不猜测 `plugin:skill` 的路径。不可用时说明并按本 Skill 的模板继续起草，不宣称已通过其校验。尊重仓库约定；没有指定位置时创建到当前 Agent 的可发现技能目录。

## 人参与的节点：确认分类

先读[分类设计](references/classification.md)，根据用户已讲清的场景给出一个具体方案：

1. 这个 OPS 服务什么范围，按什么主键分类，为什么它长期稳定。
2. 两三个真实 key 示例，以及每个 key 下用户常做的 operations。
3. key 的别名和合并规则；哪些属于共享事实，哪些只是本机实例。
4. 哪些变化自动沉淀，哪些变化需要重新确认分类。

用户已明确给出或确认这些内容时直接沿用，记录依据，不重复提问。仍有实质歧义时，用宿主交互工具或简短选项让用户选择；可以推荐，不能把沉默或默认选项当作确认。等待期间继续盘点和起草，但不落实依赖未确认分类的迁移。

默认建议：**首次确认分类标准和首批常用 operations；之后按已确认标准自动补充真实经验和同类操作。改变分类轴、拆并既有归属或扩展服务范围时再确认。** 用户要求更严格时，将“新增 key/operation 也要确认”写入目标 Skill。

把确认结果写入目标 Skill 的 `references/ops-model.md`，使用[分类决策模板](assets/ops-model.template.md)。分类目录是一份可维护的有限工作清单，只枚举用户实际要做的事，不预建平台全部能力。未验证的想法保留在模型清单中，不能冒充已验证 operation。

## 生成可以独立使用的 OPS

按需展开以下模板；替换变量和说明文字，生成后不得依赖 `create-ops` 的安装位置：

| 产物 | 用途与来源 |
| --- | --- |
| `SKILL.md` | [运行入口模板](assets/ops-skill.template.md)：触发、读取、执行、写回、安装入口 |
| `references/ops-model.md` | 已确认的分类标准、首批操作与扩展边界 |
| `references/<collection>/index.md` | 小型 key 路由，不复制知识正文 |
| `references/<collection>/<key>/index.md` | 对象共享事实、限制与 operation 目录 |
| 对象下 `operations/<operation>.md` | 一个可复用目标、前置条件、步骤、成功标准、坑与证据 |
| `references/knowledge-schema.md` | [知识与自动写回模板](assets/knowledge-schema.template.md)，按领域裁剪 |
| `references/global-agents-prompt.md` | [安装提示词模板](assets/global-agents-prompt.template.md)，填入具体触发范围 |
| `.gitignore` | 排除 `experience.local.md`、`*.local.*`、`local/` |

`collection` 使用已确认分类的自然复数，如 `sites`、`capabilities`；`key` 在文件字段中使用 `site`、`capability` 等领域名称。不要为了统一模板强迫已有 OPS 改字段、迁目录或改变可信度状态。

私有实例出现后再创建 `experience.local.md` 小型索引和 `local/` 记录。代码工具只有在确有重复、确定性需求时添加。现有脚手架和校验器适用时保留；结构检查不等于业务成功，不为形式引入后台服务。

## 自动沉淀必须成为运行流程

生成的 OPS 要明确写出 **读取 → 当前证据复核 → 执行 → 对照成功标准 → 写回唯一归属 → 同步索引 → 报告**。完成、失败或中断都有写回判断，不能等用户再说“记一下”。

- 新知识落到相应对象或 operation；具体环境和原始证据位置留在 ignored 私有实例。
- 只更新本次证据支持的结论。重复成功刷新对应验证日期；正文无变化时不复制相同步骤。
- 文档事实、源码推断、部分执行和完整验证分开；没有真实成功不得生成成功日期。
- 失效知识要修正或降级，保留必要历史证据，避免累积矛盾。
- 没有可复用新事实时说明本次无新增；不能用这句话跳过重复成功的验证日期维护。
- 写入失败、只读安装或校验未通过时，明确说明未沉淀；可以给出补丁，不能报告已经保存。

这是一份约束 Agent 行为的工作协议。文件复制不会自动执行它，也不提供宿主级的强制钩子；不得把“自动沉淀”描述为后台监控或工具拦截保证。

## 安装时建议全局前置

读取[安装与全局触发](references/installation.md)，为每个产出的 OPS 生成可直接分发的安装 Agent 提示词，并在其 `SKILL.md` 顶部提供入口。

核心句式：**无论当前使用哪个技能，只要任务涉及〔明确范围〕，都必须先读取〔目标 OPS〕，并遵循对应分类及 operation。**

安装 Agent 展示完整规则、真实全局文件和生效范围，获得明确授权后合并；已有等价授权就复用。用户仅授权创建或安装 Skill，不等于授权修改全局指令。拒绝或无答复不阻塞正常安装，不在日常使用时重复询问。

## 交付

说明实际创建或改造位置、已确认的分类、自动写回规则，以及全局提示词是“已生成”还是“已授权写入”。给一个可直接使用的调用例子。按当前授权和环境允许的检查完成结构、链接、私密信息与迁移引用核对；未执行的检查明确说明。

保留用户其他改动。自动沉淀不授予部署、付费、删数据、提交或推送权限；涉及 Cloudflare 时继续遵循对应 OPS 的禁止轮询约束，不把单一领域规则机械推广到无关领域。
