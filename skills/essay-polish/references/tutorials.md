# 教程与系列文章专项

## 先确定读者最后能做到什么

学习目标使用可观察动作，例如“能根据日志定位失败步骤”，避免只写“了解日志”。确认前置知识、运行环境及读者可投入的时间，再安排范围。

按文章类型选择证据和案例：

| 类型 | 必要内容 | 案例要求 |
|---|---|---|
| 快速上手 | 最小前提、最短成功路径、成功判据 | 可复现的最小操作 |
| 实操教程 | 场景、输入、步骤、结果、常见阻碍 | 完整上下文和关键检查点 |
| 机制解析 | 核心问题、过程、关键关系与边界 | 能解释机制的片段或输入输出示例 |
| 设计分析 | 约束、取舍、适用范围 | 必要的方案对比，不强制写代码 |
| 可复用方法 | 使用条件、模板、变体 | 至少一次具体应用，展示如何从输入得到结果 |
| 场景解法集 | 独立问题、前提、解法及限制 | 每个解法按需复现，不强行串成课程 |

查阅型参考手册可保留按功能组织的结构，只有用户要求转为教程时才重构学习路径。

## 单篇组织

根据内容自然呈现：场景与动机 → 可实现的目标 → 渐进解释或操作 → 结果核对 → 核心收获及下一步。

- 系列中用简短文字承接前文的具体成果；独立文章不虚构前后篇。
- 先让读者理解问题，再引入解决它的概念。无需人为制造痛点或贬低旧方案。
- 每次引入的新复杂度都应有必要性；第一次出现的关键概念不能留到之后才解释。
- 小结说明读者如何得到结果、现在能做什么，不机械重复标题。
- 只有真实存在且相关的下一篇才预告；完成目标的独立文章可以直接结束。

## 实操检查点

关键步骤交代以下信息，简单操作可合并描述：

> 前提与输入 → 在什么位置执行什么操作 → 预期出现什么 → 怎样判断成功 → 失败时优先检查什么。

命令注明工作目录、所需版本或版本范围及必要依赖。代码跨文件时标明文件名和连接关系；有省略必须显式标出。不要仅依靠截图传达成功条件。

能在授权环境复现时记录实际验证范围；不能执行时明确“未实测”，给出读者可执行的检查方法。不要为验证示例擅自安装依赖、使用付费服务或改动生产环境。

## 系列设计

先建立简短的章节映射，避免直接按现有素材标题拼接：

| 章节 | 解决的问题 | 前置能力 | 新获得的能力或产物 | 验证方式 |
|---|---|---|---|---|

按依赖安排顺序，尽早产生一个有意义的结果，再引入更深的机制和取舍。篇数由目标与内容密度决定，不固定为某个数量。

为相邻章节检查接缝：前一篇产物是否能成为后一篇起点；后一篇动机是否来自前一篇尚未解决的问题。角度从操作转到原理时，明确告诉读者此时要解释什么。

## 持续维护

仅在系列需要持续增长时区分主线、补充专题与读者疑问，沿用现有目录约定，不必创建空目录。

- 阻碍核心目标的缺失前提、错误和高频疑问，直接修正主线。
- 独立的深入内容作为补充，并注明关联章节。
- 尚未解决的问题记录关联位置与待确认事项；解决后更新状态。
- 根据重复、依赖断裂和学习障碍决定重构，不以补充篇数作为强制阈值。
- 保留原始资料供核对，不用重写后的教程替代全部来源。
