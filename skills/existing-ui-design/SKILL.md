# 基于现有界面迭代设计

先忠实复原已有界面，再围绕用户目标修改合适的区域。交付物应让用户看见新功能放进原产品后实际是什么样，并能操作、比较和提出修改。

## 进入任务

- 沿用用户已经提供的页面、设计稿、代码、反馈和授权。用户只想提炼方法时完成 Skill；“可能还需要几版”表达迭代需求，不自动启动几份新原型。
- 判断当前要完成的是底稿复原、候选方案、某版修订还是正式实施。缺少决定布局的输入时简短澄清，同时继续不依赖答案的采样或检查；已有依据不重复询问。
- 明确本次功能要放在哪里，以及哪些区域已被认可。默认保留现有导航、页面框架、字体、配色和核心操作位置；用户明确要求调整时按该范围修改。
- 发现已有产品组件或可运行源码时优先复用，避免制作一套难以接回产品的平行设计系统。主题资产沉淀可另用可用的 `design-styles`，本任务的首要产物是原位交互方案。

## 1. 建立可核对的底稿

按输入选择真实来源：

| 输入 | 采样与复原依据 |
| --- | --- |
| 可访问页面 | 真实浏览器中的当前可见页面、状态、DOM、样式和实际加载资源 |
| 已有设计稿或截图 | 画板尺寸、组件、字体、间距与标注；未知行为和推断参数明确记录 |
| 现有源码 | 实际组件、布局和样式；运行后核对渲染结果 |

浏览器任务先读当前环境可用的 `ego-ops`，按站点与 operation 渐进读取，再读 `ego-browser` 执行。使用真实 Ego 观察原页面、渲染整个原型、操作和验证；截图回传与任务空间隔离沿用宿主协议。依赖缺失则说明并继续离线工作，不能声称已经浏览器核验，也不能另换浏览器自动化工具。

只读采样不自动授权发送消息、创建业务记录或修改线上数据。用户已授权简单对话或采样操作时，沿用授权并验证结果，不重复确认。

从真实页面重建时，读取[页面复原与交互核验](references/reconstruction-and-review.md)，处理隐藏路由、资源与脱敏问题。截图用于对照和证据，不用整页图片冒充可交互页面。

先让底稿达到可对照状态：在相同视口、主题、内容和滚动位置检查导航、主内容、核心操作区的位置与尺寸，以及字体、密度和边界。记录仍有偏差的部分。仅凭“看起来像”不能宣称忠实复原；只有截图时不声称采集了真实 DOM。

## 2. 在原界面中设计

为新增功能选择与原任务流相容的容器，例如现有消息、详情区、列表、抽屉或弹窗。选择依据是用户从哪里进入、要做什么、完成后回到哪里；不把某次成功的卡片布局变成所有产品的固定答案。

新增内容沿用原组件语言；原来能完成的核心操作仍应可达。把评审用的版本切换、前后对照和反馈入口与产品功能区分清楚，避免评审工具成为正式界面的一部分。

原型里的关键路径要能走通，有可观察的状态变化。没有后端时使用清楚标识的演示数据；“发送”“保存”等演示行为不能被描述成真实业务接入。

## 3. 多版比较与连续修订

- 用户明确要多版时，按其数量提供；只说“几版”可先做 2–3 个有实质区别的候选。只是修正某一版时沿该版继续，不强制重新发散。
- 所有候选共享底稿、代表性内容和任务状态；区别集中于待解决的问题，例如信息展开方式、入口位置或操作步骤。不要用换主题、重做导航或不同样例内容制造虚假的方案差异。
- 每版说明改变了什么、解决什么问题、主要代价以及尚未决定的点。推荐一版时给出与用户目标相关的依据。
- 用同一预览内的版本切换、原版对照或并排比较方便审阅，并保持当前比较状态尽量一致。原始基线与已认可版本分别保留，不被下一次修订覆盖。
- 接到反馈，先判断问题属于产品适配、视觉、信息结构还是交互故障。用户说“用不了”时，对照真实产品检查是否根本无法嵌入，不直接假设只是按钮或保存缺陷。
- 下一版保留已认可部分，针对明确反馈修改。简短记录版本、认可内容、否定内容、待定点及后续改动；复用已有任务记录，不另造一套进度系统。

### 认可与实施

“方向对”只确认设计原则；选中某个候选只确定继续迭代的基础。最终定稿及正式实施范围以用户实际指令为准，不推定，也不要求用户使用固定口令。

若用户已经授权设计后直接实施，并给出足够明确的验收依据，按授权继续；若用户要求先看稿再确定，则完成可审阅原型后等待具体反馈。不要用本 Skill 添加重复审批，也不要把草稿认可写成产品实施完成。

## 4. 验证和交付

- 在 Ego 中验证每版有差异的关键路径及共用的核心路径。操作后检查用户可见结果；有保存功能时核验关闭重开、刷新，有返回路径时核验返回后上下文。
- 按目标设备检查实际元素边界、遮挡、输入框可用性和弹窗滚动。不能用页面没有横向滚动条代替这些检查。
- 通过用户所在设备可访问的方式交付；远端会话不能只给 localhost。Happy 静态预览使用宿主提供的 create/publish 工具与其返回的工作区，遵循生命周期和公开内容约束。多版尽量放在同一快照，旧预览未经授权不关闭。
- 保留可继续编辑的源码及比较记录；发布快照或临时目录不自动等于持久化源文件，按实际情况报告位置与寿命。
- 交付时列出候选入口、主要差异、验证范围及待定点。区分原型可交互、真实数据接入和正式产品 E2E；只有实际完成的部分才标为通过。

如果后续进入实施，把选定版本、关键交互状态、复用组件及验收路径交给实现任务，避免开发时再次自行改版。
