# readme-craft

把一个 GitHub 仓库首页做成**一眼吸睛、少字精准、靠真实证据说话**的作品展示页，并在逐个仓库的打磨中持续沉淀你的个人审美偏好。

> 核心公式：**好看的真实素材 + 精确克制的文案 + 恰到好处的实机视频**，全部服务于同一条主线——**3 秒吸引眼光，30 秒让读者相信这个项目有独特价值。**

## 适用模式

动笔前先明确本次范围（用户已说明则直接进入，不要重复追问）：

1. **整页重塑（默认）**：梳理核心动机与阅读顺序 + 制作项目原生视觉/视频 + 重写精炼 README。
2. **仅做素材**：只产出 Hero、分层拆解图、作品墙或实机 MP4，不改动现有 `README.md` 正文。
3. **只读诊断**：只分析现有 README 的信息顺序、视觉短板与删改建议，不修改文件。

## 核心工作流

### 1. 先侦察仓库，绝不凭空编造
- 读取现有 `README.md`、目录树、入口源码、部署/档案文档、已有截图与渲染资产。
- 提取 5 项项目事实：目标读者、真实产出/证据、最短上手路径、技术或工艺亮点、客观边界。
- 严格排除私有信息：本机绝对路径、凭据、原始日志与未公开数据不得进入 README 或素材。

### 2. 动笔前必须对齐作者意图（关键闸门）
光看代码往往看不出仓库真正的灵魂（例如“为什么做这个项目”“它是想展示成品、验证探索，还是推广一套可复用方法”）。在重写整页前，若对话中尚未明确，**先给出一份简洁的板块草案，并一次对齐最多 3 件事**：
1. **核心动机与亮点**：这个项目最想让陌生人一眼看懂的价值是什么？
2. **读者重心**：偏「先体验审美、后工艺拆解」，还是偏「纯作品展示 / 纯开发者上手」？
3. **语言与媒体偏好**：中文 / 双语？是否需要实机 MP4 或真实素材分层图？

> 如果用户明确要求“直接先出一版看效果”，则按最佳实践先出初稿并在开头一句话说明假设，绝不为琐碎细节反复打断。

### 3. 读取个人审美档案与视觉规则
开始出图与写稿前，按需加载：
- 必读：[references/taste-profile.md](references/taste-profile.md)（复用已确认的审美偏好与避坑红线）。
- 制作视觉图、Hero 或录制 MP4 前读：[references/visual-and-media.md](references/visual-and-media.md)。

### 4. 定调与选证据（一类项目一种视觉语言）
从项目自身提炼配色、字体、材质与母题，**绝不套用统一模板**。按项目类型决定主证据形态：

| 项目类型 | 主证据组合 | 典型节奏 |
|---|---|---|
| **设计 / 视觉 / 作品集** | 项目原生 Hero + 真实作品墙 / 对比图 | 静态高清视觉已足够证明，不强行塞视频 |
| **交互 / 工具 / CLI / 网页应用** | 项目原生 Hero + GitHub 原生可播 MP4 + 关键机理视觉图 | Hero 定调 → 两句定位 → MP4 演示 → 原理/操作表 → 上手 |
| **方法论 / Skill / 架构库** | 项目原生 Hero + 前后对比 / 分层拆解图 + 真实案例清单 | 展示真实落地产出，再展开使用命令与边界 |

### 5. 视觉与文案并行落地（硬性纪律）
- **视觉挑大梁，拒绝“文档风流程图”**：
  - 严禁用大量纯文字矩形框画“说明书式流程图”。
  - 原理图/工艺图优先采用 **Hybrid 混合出图**（HTML/CSS 排版骨架 + 嵌入项目真实的透明渲染图/界面截图/输出样张，经无头浏览器高清渲染为 PNG/WebP），**整图尽量少字**，让真实画面代替大段解释。
- **文案做减法，真诚胜过堆砌**：
  - 首屏用 1~2 句话讲清“做什么 + 凭什么特别”，紧跟直达入口。
  - **优先设立简短真诚的「动机」板块**：尤其对个人作品、内容合集或创意实验，用自然人话交代真实起因、为什么采用当前形态、以及它帮读者解决了什么具体痛点，比罗列冰冷指标更有感染力。
  - **去掉生硬赘词与数据堆砌**：不要在首屏和正文反复堆叠“非官方”“免责统计口径”“字节数/哈希”等官话定词；客观边界与版权归属放到文末用 1~2 句克制说明即可。
  - **按项目性质控制代码篇幅**：非纯开发者工具（如图集、体验型作品、内容站点），正文中**代码尽量少**，安装与部署命令收进文末 `<details>` 折叠，不让命令行抢走作品气质。
  - 操作方式、源码模块、方案对比优先用紧凑 Markdown 表格，避免大段散文。
  - 首页视觉锚点保持 **2~3 处分工明确**（如 Hero 定调 + 原生 MP4 或展示大图），严禁 Hero + GIF + 同内容视频重复堆叠。
- **保留可复制、可搜索的 Markdown**：绝不把整页 README 栅格化成一张大图；命令、链接、表格与边界说明必须留在 Markdown 正文。
- **工作区与发布边界**：优先在独立分支或 worktree 修改并本地预览，**未经用户明确同意不直接 commit、push、提 PR 或合并 `main`**。

### 6. 渲染验收与审美沉淀
交付前必须完成两项硬核验：
1. **运行自动化检查**：
   ```bash
   python3 scripts/audit_readme.py /path/to/repo/README.md
   ```
2. **人工目检渲染图**：把新生成的 PNG/WebP/SVG 实际打开检查（确认无文字裁切、无元素遮挡、深浅背景可读、比例协调），并直接发图给用户预览。
3. **沉淀反馈**：用户对成品给出明确审美评价或微调意见后，提炼 1~2 条可复用规律追加回 [references/taste-profile.md](references/taste-profile.md)。

## 质量红线

- 首屏 3 秒能看出项目气质与价值，不依赖读者已有背景知识。
- 去掉仓库名后，主视觉与机理图仍明显属于这个项目，而不是通用模板。
- 所有视觉素材均源自真实项目（真实界面、渲染层、实机录屏或代码输出），不编造数据与背书。
- 操作类 MP4 必须通过 GitHub 原生附件 URL 独立成段嵌入，确保首页可就地播放，不用相对 `.mp4` 链接充数。
- 最终 README 比改前更精炼、更有记忆点，而不是字数膨胀或装饰堆砌。
