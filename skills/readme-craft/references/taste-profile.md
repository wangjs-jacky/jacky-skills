## 已确认的个人偏好

- **核心观感**：**吸睛、少字、高质感**。README 的首要任务是让人第一眼想看下去，而不是写一份冗长说明书。
- **信息节奏**：面向既有审美又有工程含金量的项目，偏好 **「先体验审美、后工艺拆解」**——上半场先给视觉与实机演示，下半场再点出核心机制、源码入口与上手命令。
- **价值挖掘与真诚表达**：动笔前必须先和作者对齐「为什么做这个项目 / 最想突出的核心亮点」，并在个人作品/内容类仓库里专门留出简短真诚的 **「动机」** 板块，用人话讲清起因与使用场景（如快速重读、社媒分享），显得真诚有温度。
- **克制数据与代码**：少在正文堆砌冷冰冰的统计口径、哈希值或“非官方”等生硬定词；非开发者工具类仓库尽量减少正文代码块，把本地运行与部署命令折叠收纳。
- **视觉载体**：能用真实素材（真实 3D 渲染图层、洁净界面、真实输出）拼出直观视觉对比时，优先做 **Hybrid 混合大图**，大幅压缩图内文字。

## 明确避坑红线

1. **禁止“文档风文字框流程图”**：纯 SVG 里塞 6~7 个带多行小字的方框，视觉上像内部架构文档，不够吸睛（2026-11-24 `paper-room-typewriter` 复盘确认）。
2. **禁止首页媒体重复堆叠**：不要把静态 Hero + 同内容 GIF + 不可播放的视频链接全堆在首屏；Hero 负责定调，原生 MP4 负责动态演示，各司其职（2026-11-24 `paper-room-typewriter` 复盘确认）。
3. **禁止矫枉过正砍成空壳**：精简不等于把核心工艺和项目动机全藏进 `<details>`；真正决定项目含金量的核心亮点必须留在主视线内。
4. **禁止浮层遮挡真实界面**：往实机截图上叠说明标签时，不可盖住原 UI 按钮或核心交互区。
