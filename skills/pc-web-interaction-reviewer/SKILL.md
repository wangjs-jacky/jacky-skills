# PC Web 交互评审专家

把网站当作桌面产品使用，以真实证据、视口边界和可观察变化为准。默认只读评审；用户明确要求修复时，才把确认问题交给后续实现任务。

## 先确认平台边界

1. 本 Skill 只评审桌面宽屏与键盘、鼠标或触控板交互。输入明显是手机状态栏、原生 App、窄屏 Mobile Web 或单手触控流程时，停止套用桌面量规并改用 `$mobile-app-interaction-reviewer`。
2. PC 可以利用更大的横向空间、多栏、锚定 Popover，以及同时支持鼠标悬停和键盘焦点的 Tooltip 来承载次要说明、快捷键或被截断的完整值。
3. Hover/Tooltip 不能成为关键动作、当前状态、错误原因或完成任务所需信息的唯一入口；鼠标悬停有价值时，键盘焦点必须能获得等价内容。
4. 跨端任务使用同一业务 Case ID，但 PC 与 Mobile 分别选择容器、密度与信息披露方式并分别给 verdict，不能用一个端的截图证明另一个端通过。

## 先选择工作模式

每个评审阶段只声明一个主模式。复杂任务可以按“截图基线 → E2E 走查 → 修复后回归”串联，但必须分阶段执行、分开记录证据，不能用一个模式的证据替代另一个模式。

| 主模式 | 何时选择 | 必须读取 |
|---|---|---|
| 截图评审 | 输入是截图、录屏指定帧或其他静态画面，目标是判断当前可见的视觉、布局和桌面适配问题 | [screenshot-review.md](references/screenshot-review.md) |
| 全站交互 E2E 走查 | 输入是 URL 或可运行构建，要求遍历页面、点击入口并判断动作前后变化 | [full-site-e2e-walkthrough.md](references/full-site-e2e-walkthrough.md) |
| 回归验收 | 已有问题 ID、验收点或 Case，目标是按原路径复跑并判定修复结果 | [regression-acceptance.md](references/regression-acceptance.md) |

指定单条用户路径但没有既定 Case 时，使用“全站交互 E2E 走查”的限界版本，只覆盖该流程及必要的关闭、返回和异常路径。只有已存在明确验收点时才进入“回归验收”。

三种模式都按需读取 [desktop-review-rubric.md](references/desktop-review-rubric.md)：截图评审只使用可由画面证明的条目；E2E 与回归使用相关的页面、交互、视口、键盘和状态矩阵。

需要独立调用、Agent 委派或三种模式的可复制任务模板时，读取 [prompt-examples.md](references/prompt-examples.md)。

## 全局执行规则

### 独立性与证据

1. 不把生产者自评、工具“成功”文本或页面跳转本身当作通过证据。
2. 区分“画面可见事实”“运行态观察”“用户确认”和“待验证项”；证据不足时不得猜测。
3. 正式检查前先找最大内容、最大无效空白、最小文字、长期占位区域和最孤立入口；多栏工作区还要逐栏登记用途、当前内容、占宽、可见收起入口和恢复路径，避免局部细节掩盖主导问题。
4. 每条确认问题都要包含位置或 Case、复现动作、实际结果、影响、PC 预期、严重度和证据；结论只使用“通过 / 不通过 / 证据不足”。

### 浏览器与执行路由

- 需要操作真实页面时，先加载 `ego-ops` 并按站点与 operation 读取经验，再加载 `ego-browser` 执行；登录态、授权、任务空间和证据归档遵循这两项 Skill。
- 不能仅根据 URL 推断无需登录态；根据用户当前说明与已有站点经验核对需求，仍不明确且影响评审结果时再询问，并记录判断来源。
- 需要生成或执行自动化 E2E 时，可委派 `web-e2e`；交互评审结论仍以本 Skill 的覆盖表、前后状态与视觉证据为准。
- 只加载当前模式及实际委派链需要的 Skill 或 reference，不预读所有模式。

### 安全门

- 可直接执行只读动作：打开、截图、读取结构、滚动、展开、切换视图、查看 Console 与 Network。
- 提交、保存、删除、授权、支付、上传、发送消息或其他会改变服务器、账号、持久数据的动作，必须先获得用户确认；未获确认时记录为未覆盖。
- 只关闭本轮新开的标签页，不关闭用户原有页面；证据不得包含凭据、Cookie、请求头、密钥、个人信息或敏感页面正文。

## 反馈与经验

每次先独立完成视觉主矛盾扫描，再读取
[review-feedback-loop.md](references/review-feedback-loop.md)
的“当前生效规则”补漏。用户明确纠正评审结果时，按该 reference 更新
[review-feedback-cases.md](references/review-feedback-cases.md)；产品、账号或本机特例只写入同目录
`experience.local.md`，不写入共享 reference，也不提升为通用规则。

通用反馈沉淀在本 Skill 仓库，不写入个人 auto memory。历史案例不是当前页面证据。评审带有已知反馈基线的产品时，盲测阶段不得读取 `experience.local.md`；必须先完成评审并冻结独立发现清单，再按需读取其中对应产品的基线进行补漏、对照或回归。文件不存在或没有对应基线时直接跳过，不得为此猜测预期答案。

## 完成门

- [ ] 已声明主模式，并读取对应 reference；多阶段任务的证据没有混用。
- [ ] 已确认这是桌面宽屏任务；原生移动端和窄屏 Mobile Web 已路由到独立 Mobile reviewer。
- [ ] 已按证据边界输出结论，没有把静态截图当成交互 E2E。
- [ ] E2E 已先建立“页面类型 × 数据/任务状态”矩阵，覆盖核心任务的代表性动态状态；缺少活跃详情、已填充列表等关键状态时，没有声称全站完成。
- [ ] E2E 已记录入口覆盖和动作前后变化；回归已逐 Case 判定且没有无边界探索。
- [ ] 多个可见 UI Case 已按“一项一组”交付独立前后截图；整页总览没有代替逐项证据，截图组数与可见 Case 数一致。
- [ ] 前后截图保持相同 CSS 视口、DPR、缩放和裁切比例；共享 Header、侧栏等联动区域已用真实页面及相关断点验证，未用孤立 fixture 代替集成证据。
- [ ] 多栏工作区已逐栏检查当前价值、空状态、独立收起、空间回收和恢复入口；有窄屏或移动端对照证据时，已核对核心能力是否无说明消失。
- [ ] Hover/Tooltip 只承载次要信息且同时支持键盘焦点；关键能力没有被藏成 hover-only。
- [ ] 关键浮层已与页面现有 PC 基线对照字体层级、信息密度、间距、圆角、分割线、阴影和交互状态；没有把局部“更醒目”误判为整体一致。
- [ ] URL 任务的登录态已由用户说明、本地精确记录或明确上下文确定，没有根据 URL 外观自行推断。
- [ ] 浏览器委派、安全门、证据脱敏和用户原有标签页均符合全局规则。
- [ ] 所有“待验证”都包含验证问题、动作及通过/失败标准。
- [ ] 已向调用方返回逐 Case verdict、证据、产物、风险和下一步；没有越权创建 PR、等待 CI 或合并。
