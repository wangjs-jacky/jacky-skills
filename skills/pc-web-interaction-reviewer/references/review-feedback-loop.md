# PC Web 评审反馈闭环

> 把用户对评审结果的明确纠正转成可追踪、可复用、能够改变下次行为的规则。

## 使用时机

- **每次开始评审时**：先依据主 Skill 独立完成视觉主矛盾扫描，再读取“当前生效规则”补漏；不要先读历史案例。
- **收到用户反馈后**：读取本文和
  [review-feedback-cases.md](review-feedback-cases.md)，完成差距归类、案例追加和规则更新。
- **没有用户明确反馈时**：只应用规则，不自行追加案例。

历史反馈是观察提示，不是当前产品事实。不得因为旧案例出现过某个问题，就在新截图中无证据复述。

## 自更新流程

### 步骤一：拆分证据等级

把反馈中的信息拆成三类：

1. **截图或录屏可见事实**：可以直接进入视觉评审，但仍标注置信度。
2. **用户确认的产品事实**：例如用户明确说明“左侧栏没有收起功能”；记录为“用户确认”，不要伪装成截图发现。
3. **运行态未知项**：例如无法从截图判断右栏是否始终为空；转成明确的验证问题、动作和判定规则。

### 步骤二：比较上一版结果

每个反馈点只能归入一个主要类别：

| 类别 | 定义 |
|---|---|
| 命中 | 上一版明确指出同一问题、影响和正确方向，且优先级合理 |
| 部分命中 | 提到了相关现象，但遗漏根因、具体区域、验证交接或优先级不足 |
| 漏评 | 上一版没有覆盖该问题 |
| 过度推断 | 证据不足却写成已确认事实，或给出超出证据的结论 |
| 优先级偏差 | 问题可能成立，但挤占了更主导问题的位置 |

### 步骤三：只提升可泛化规则

一条反馈要进入“当前生效规则”，必须同时满足：

1. 能用于多个 PC Web 产品或页面。
2. 能改变观察顺序、证据表达、问题优先级或验证动作。
3. 不依赖某个产品名称、内部实现或一次性的页面数据。

仅适用于特定产品的问题写入对应产品基线。涉及私有或带公司属性的信息不得写入共享 Skill。

### 步骤四：追加案例

在 [review-feedback-cases.md](review-feedback-cases.md) 末尾追加案例，至少记录：

- 日期和证据；
- 用户反馈摘要；
- 命中、部分命中、漏评、过度推断和优先级偏差；
- 新增或调整的规则 ID；
- 下次如何验证规则真正生效。

保留用户原意，但使用概括表述；不要复制敏感信息、令牌或无关上下文。

### 步骤五：更新和淘汰规则

- 新规则使用递增 ID：`FR-001`、`FR-002`。
- 规则含义变化时，在案例中记录原因，再修改本文。
- 两次以上反馈证明规则导致误报时，将其移入“已停用规则”，不要直接删除历史。
- 规则重复时合并，不为同一件事堆叠近义检查项。

## 当前生效规则

### FR-001：先检查主内容的比例关系

第一轮先找出最大内容元素、最大无效空白、最小文字、最长占位区域和最孤立控件。在检查文字细节前，比较图片、视频、代码块、文本和空白在有效工作区中的相对尺度。媒体在移动端合理，不代表原尺寸进入 PC 对话仍合理。

至少回答：

- 媒体宽高相对会话内容列是否过大；
- 正文与媒体是否形成明显的“小字配大图”；
- 大媒体是否导致单屏只能看到极少上下文；
- 问题是否可能来自移动端固定尺寸或断点缺失。

对图片结果补充方图、横图、竖图和多图场景的默认预览、放大、关闭与焦点恢复契约。截图只能说明“呈现出类似移动端尺寸直接延续的特征”；只有用户或实现证据确认后，才能把移动端适配写成事实根因。

### FR-002：逐栏检查固定区域的价值和独立收起能力

对左栏、右栏、检查器等长期占位区域分别检查：

- 当前内容价值是否配得上占用宽度；
- 是否存在可见的折叠入口；
- 折叠后主工作区是否回收空间；
- 空状态是否仍强制占位；
- 折叠状态是否记忆，以及如何恢复；
- 不能用一个栏的入口或一句“左右栏可折叠”替代逐栏证据。

截图没有出现折叠入口，只能写“截图中未见”，不能直接证明产品没有折叠能力。用户明确确认时，使用“用户确认”作为证据。

侧栏或辅助区不一定有可见边框。核心内容旁的大块单侧空白、贴边入口或不对称闲置侧翼也要进入区域盘点；无法确认结构时输出状态、内容来源、跨断点对应能力和收起行为的验证任务，不能直接写“没有面板”后跳过。

### FR-003：空面板必须区分状态问题与结构问题

看到大面积空白时，不立即断言设计错误。向调用方交接三个问题：

1. 什么操作或数据会让面板出现内容？
2. 面板是持续保留、按任务展开，还是空时自动收起？
3. 用户能否主动关闭、折叠或调宽？

若面板长期为空、持续占宽且不可收起，判定为桌面空间利用问题；若它只在相关任务中展开且退出路径清晰，则空状态本身不构成问题。先确认状态模型，再选择自动收起、手动折叠或默认窄态，不要从单张截图锁定唯一方案。

有移动端、窄屏实现、产品说明或用户确认可对照时，还要检查同一核心能力是否在 PC 无说明消失。容器和布局可以不同；功能缺失必须记录为能力一致性问题或规格待确认，而不是把大面积空白只当视觉问题。

### FR-004：孤立图标和全局模式入口都要检查发现性

对单独出现的加号、返回、更多或模式图标，比较其尺寸、描边、容器、对齐、留白和邻近关系，并让评审者在不了解产品内部名称的前提下说明其大致用途。不能只写“难看”，必须说明它与同层级控件如何不一致，以及这种不一致是否造成错误分组、抢夺注意力或入口难以理解。

对禅、沉浸、专注等全局模式，额外检查用途说明、启用状态和退出路径。截图中缺少文字、邻近上下文或状态表达，可以判定当前画面的发现性不足；真实功能、Tooltip、可访问名称和切换行为仍作为运行态复核项交接。

补上可见文案只解决语义，不自动代表视觉验收通过。图标或全局动作完成第一次修复后，还要再次比较轮廓重量、符号气质、容器形态、相邻按钮主次和整组间距；若主操作仍像中性工具图标、描边明显重于同层控件，或与相邻次操作形成不了清晰层级，应保持问题未关闭并提供聚焦前后证据。

### FR-005：主导比例问题优先于局部微观问题

排序“最值得先改”时，先处理影响整屏阅读和空间分配的问题，再处理输入框高度、选中态、状态圆点等局部细节。若一个问题控制了主要视觉面积，应说明它为何主导体验。

### FR-006：待验证项必须可交接

每个未知项必须包含：

- 验证问题；
- 建议操作或需要补充的证据；
- 通过与失败的判断标准。

目标是让调用 Skill 的 Agent 可以直接继续复核，而不是收到一句无法执行的“待实测”。

截图顶边、容器边缘的半行或半张卡片不能单独证明固定栏遮挡。先验证截图裁切与滚动位置；只有运行态或稳定画面重叠证据才能升级为遮挡缺陷。

### FR-007：先确认 URL 是否需要复用已有登录态

URL、IP 地址、路由名称和页面可达性都不能单独证明页面无需登录态。开始 E2E 前按以下顺序确定：

1. 优先使用用户当前请求中的明确说明。
2. 没有明确说明时，按 `ego-ops` 的站点与 operation 经验核对登录态需求。
3. 未命中且选错会改变页面状态或评审结果时，先问用户是否必须复用当前 Chrome 的已有登录态。
4. 记录“是否需要已有登录态”和判断来源，再按 `ego-browser` 选择任务空间。

用户当前确认覆盖历史记录；按 Ego 的隐私规则保留必要证据，不记录凭据或敏感参数。

### FR-008：全站完成受页面 × 状态覆盖约束

全站走查先建立“页面类型 × 数据/任务状态”矩阵，再建立点击入口清单。路由遍历和入口遍历不能替代状态覆盖。

至少检查：

- 核心任务是否进入一个代表性的已填充、详情或活跃状态；
- 空状态、静态壳和动态实体是否被错误合并计数；
- 新状态是否重新盘点多栏布局、长期空置区域和全局模式入口；
- 关键状态不可达时是否写明阻断原因，并把总结果降为“证据不足”。

只走过登录后空状态或自动化脚本跑完，不得声称“全站完成”。

### FR-009：多个可见问题必须逐项交付前后截图

当一次修复或验收包含多个可见 UI Case 时，建立 `Case ID → 修复前截图 → 修复后截图` 证据矩阵，并满足：

- 每个可见 UI Case 都有一组独立、可定位的前后证据；
- 整页总览只能说明整体上下文，不能同时充当多个 Case 的唯一截图；
- 同一张原始画面可以复用为素材，但必须按 Case 独立裁切或标注变化区域；
- 折叠、展开、恢复、选中等状态型交互按需要增加状态帧，不能用静态默认态代替；
- 交付前比较可见 UI Case 数和独立截图组数，数量不一致时不得写“截图证据完整”。

这条规则约束的是证据颗粒度，不要求为了凑数量制造重复截图。纯逻辑、不可见后台或同一视觉变化下的多个技术断言可以共享证据，但必须在 Case 表中说明共享理由。

### FR-010：视觉回归证据必须可比且覆盖真实集成

前后图先核对 CSS 视口、DPR、浏览器缩放和裁切比例。比例不同会放大图标重量、圆角和间距差异；未统一或明确归一化时，只能证明元素存在，不能证明视觉优劣。

独立 fixture 只能证明组件本身。若控件位于共享 Header、多栏工作区、浮层锚点或响应式重排区域，至少再验证一个常用视口和一个相关断点下的真实页面构成，测量相邻命中区域并检查内容截断。没有真实集成证据时，不得用“按钮自身截图正常”推出“页面无拥挤或层级已收口”。

### FR-013：主验收录屏必须以成功结果收口

正向主流程与异常回退都需要录制时，不能把两者混成一个以错误状态收尾的“主验收”视频。否则即使脚本先完成成功路径，观看者仍会合理理解为最终操作失败。

- 主验收视频只覆盖正常路径，并停留在足以判断成功的可观察结果上，例如新页面、成功状态或已创建实体。
- loading 等瞬时反馈需要在主视频中可辨认，但不能以中间 spinner 或页面重载代替最终成功结果。
- 故障注入、错误弹窗与恢复行为使用单独命名的 negative-path 证据，并在相邻文字中明确说明注入条件。
- 交付前抽取主视频最后一帧；若最后一帧是 Error、空白页、全屏 loading 或无法判断的过渡态，不得把它标为成功验收。

### FR-014：现有产品的设计稿必须以真实页面为不可变基线

为已有 PC Web 产品制作局部改版或交互设计稿时，先在用户指定或产品常用视口采集真实运行页面，并登记持久导航、栏宽、主题、字号、密度、背景和相邻控件。设计稿默认保留这些非目标区域，只对本次目标组件做差量修改。

- 不得从记忆、通用设计系统或参考产品重新绘制整套应用壳，再把它称为该产品的真实设计稿。
- 若只能制作独立 fixture，必须明确标注为组件概念稿；它不能证明与真实产品的视觉一致性。
- 验收时把真实基线与设计稿设置为相同 CSS 视口、DPR 和缩放，逐项比较导航结构、主要栏位边界、主题颜色、文字层级和目标组件位置。
- 真实页面不可达时，说明缺失证据并请求截图或访问条件；不得用想象补齐产品基线。
- 参考产品只提供目标交互模式，不覆盖当前产品自身的视觉语言和空间结构。

## 已停用规则

### FR-011：逐项证据必须进入实际 PR 并在合并后可用

已停用。逐 Case 可比证据仍由 `FR-009` 和 `FR-010` 约束，但 PR 正文、CI 与合并属于上层交付编排，不再由交互 reviewer 重复拥有。历史案例保留用于解释职责调整。

### FR-012：媒体验收必须检查用户语义，不能只验证播放能力

文件、图片、动态照片、音频和视频共用底层事件或工具协议时，评审必须同时检查可见类型名称、图标、文件名、动作入口和实际行为。底层事件名、工具名或 MIME 兜底名不能直接冒充用户可见类型；即使媒体能够加载和播放，错误显示 `file`、`attachment`、工具名或内部 kind 仍属于未关闭的语义问题。

回归时至少回答：

- 当前标题或标签表达的是用户理解的对象类型，还是底层协议实现；
- 移除内部标签后，文件名、来源或播放/下载入口是否仍足以识别对象；
- 同一规则是否误伤 PDF、音频和真正的通用文件卡；
- 自动化是否直接断言错误内部标签不存在，而不是只断言播放器出现。
