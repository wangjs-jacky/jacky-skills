# 提问前的匹配与裁决

## 先标准化当前决定

描述 `目标 + 当前状态 + 待选动作 + 对象/影响`。例如：“为当前任务发布新静态稿；当前预览槽位满；是否关闭同任务已被替代的旧快照以释放一个槽位”。不要用“是否选推荐”作为描述。

先分辨这是**选择偏好、流程委托、动作许可、事实询问，还是需要本人完成的动作**。后三种不能因为历史答过“是/ok”就当作推荐选择。事实按其对象、用途、时间和证据复核；必要时引用领域 OPS 中的原事实，不能发明“已获许可”。登录、人机验证等必须有当次真实完成证据。

最小匹配上下文：

| 字段 | 作用 |
| --- | --- |
| scenario / operation | 先缩小要读取的决策库 |
| user / project / task | 确认谁的决定、对哪个目标有效；未知不按通配处理 |
| resource / environment | 要变更什么、是本地草稿/测试/生产、目标是否受保护 |
| trigger / preconditions | 是否真达到触发条件、候选对象如何筛选 |
| proposed_action / effects | 当前方案的语义、成本、公开范围、服务和数据后果 |
| source_skill / tool_contract | 发问来源及不能被本规则替代的工具要求 |

规则未约束的字段可以不参与匹配，但**关键动作对象与授权范围不得靠缺省推测**。无需每次收集完整设备档案。

## 决策顺序

1. 按实际指令层级执行。先处理当前用户明确选择、撤销、保留项及适用的强制门槛；旧规则不能覆盖新要求。
2. 当前任务已经明确授权且没有新的实质选择时直接继续；无需先学习新规则，也不要为了使用 OPS 制造问题。
3. 从同 scenario/operation 的个人记录选择 `active` 规则，校验来源、有效期、撤销/替代关系、全部前置条件和例外。
4. **同一指令层级内**，更具体且条件满足的规则优先：当前任务 → 项目/对象 → 场景通用偏好。宽泛的“按推荐”不能压过明确的保留对象。两个无法消解的有效规则相撞时，只澄清冲突点，不用分数相加或简单“最新胜出”。
5. 偏好规则只能决定选项。动作授权必须另外来自当前任务或适用的 `action_grant`；已明确持续授权无需每次重问。结构检验通过、重复成功和模型高置信度均不能生成授权。
6. 根据结果继续或询问，并把本次采用的规则及未命中的关键条件保存在必要证据中。

## 四种结果

| 结果 | 行为 |
| --- | --- |
| 已有答案 | 有效同范围选择/委托，所需执行授权也齐全：直接继续 |
| 只能推荐 | 有偏好但缺本次必要授权/事实：先准备具体方案，只问缺失项 |
| 首次决定 | 新的真实决策点且没有已授权的默认处理：问一次；人答复后自动沉淀 |
| 不能代答 | 宿主强制审批、身份动作、明确要求当前人工验收或指令冲突：说明出处，保留门槛，不代填通过 |

## 推荐的正确用法

“通常采纳 AI 推荐”可帮助排序、减少选项数量。仅当当前用户或有效规则明确委托了**此范围内**的选择时，才自动采用满足目标的推荐方案。若只需要可逆的常规实现判断，沿任务授权直接判断即可。

不要把历史“A 方案”绑定为未来第一项，也不要把“推荐”标签绑定到具体动作。每次重新核对推荐理由与约束；推荐方案偏离已定目标，先修正方案。用户曾否决的路线不能借一个新名字重新自动选入。

## 失效与更正

用户说“这次例外”只作用于本次；“以后不要这样”撤销对应持续规则；表达范围含糊时停止使用受影响规则，问清变更的范围，同时继续不依赖该决定的工作。重大资源、项目、环境、费用或公开范围变化需要重新匹配，不机械套用。

每次使用事件触发复核；不建后台扫描、轮询或定期催问。临时连接异常不自动撤销用户偏好；执行失败记录为失败，并停止无授权的破坏性重试。
