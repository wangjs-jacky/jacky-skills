# 发布精确版本的 npm 包

## 目标

向指定 registry 发布目标包的精确版本，并核对渠道和产物。

## 前置条件与授权

读[平台档案](../index.md)，明确源码提交、package/workspace、版本来源、访问级别、dist-tag 和 CI/本机路径。复核实际 workflow，不能固定要求某文件名、Token 或本机登录。

## 流程与检查点

1. 核对项目配置、工作树与待发布版本，确认已有版本状态。版本存在时先比较当前目标，不自动升版本或复用旧版本号。
2. 按任务授权与项目流程准备产物，检查 lifecycle 脚本；复用有效构建/pack 证据。确需预览包内容时采用当前工具支持方式，不能假定 dry-run 没有脚本副作用。
3. CI 路径核对精确触发 ref、workflow、包目录、身份与允许动作，只触发一次已授权发布；本机路径使用项目当前发布命令和明确 registry/access/tag。不要同时再本机发布相同版本。
4. 用精确版本查询，例如 `npm view <package>@<version> version dist.integrity --registry <registry>`，并单独核对目标 dist-tag 指向；不只查询 latest。
5. 将返回产物信息与本次预期包核对。若任务声明安装可用，需要相应有效证据；未获测试/试装授权时不执行它，也不宣称功能已验证。

## 成功标准

精确 registry、包名、版本及目标渠道符合要求，发布产物信息与本次来源相符。只有 tag 推送或 CI 绿色而缺少 registry 证据时保持未完成；功能可用的声明必须有对应证据。

## 坑与恢复

网络/超时报错先读回版本状态。版本已存在但产物不符时说明冲突，不盲重发或覆盖。发布部分成功时保存各包/平台结果，后续只处理缺失目标。需要分阶段发布时按项目和当前平台说明处理，不把 staged 状态当作公开发布。

## 证据与边界

依据 2026-10-15 官方 npm 文档，尚无本操作的完整运行证据。项目历史成功日期只保留在对应实例，不迁移为本次成功。按[写回协议](../../../knowledge-schema.md)维护。
