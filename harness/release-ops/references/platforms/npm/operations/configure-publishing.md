# 配置 npm 发布链路

## 目标

为指定包建立与项目实际环境匹配的发布配置，明确首次真实发布是否已验证。

## 前置条件与授权

读[平台档案](../index.md)。明确目标 registry/包、公开或受限访问、运行环境、工作流、版本/tag 约定与发布权限；配置授权不自动允许发一个试验版本或替换所有认证方式。

## 流程与检查点

1. 读取现有 package 配置与实际 workflow，确认是否已有有效链路。只检查认证模式和凭据来源名称，不打印 `.npmrc` 或 Token。
2. CI 已使用 Trusted Publishing 时核对平台支持、runner 类型、Node/npm 门槛、信任绑定与允许动作；GitHub job 的 OIDC 权限、workflow 文件名、repository 和 environment 与包配置一致。
3. 新配置在适用且已授权的环境中选择当前支持的方式。现有有效 Token/交互方式先理解项目要求，不自动迁移或删除。首次包不存在或特殊 registry 时核对其当前初始化路径，不假设现有包设置一定可用。
4. 复用项目构建/发布脚本，明确包所在目录、触发条件、发布渠道、检查要求及 Secret 引用。版本更新或推送 tag 可能触发真正发布，执行前确认属于当前范围。
5. 读回修改后的配置与平台侧关联。只完成配置时记录“配置已核对，首次真实发布待验证”；真实发布已授权则转[发布包](publish-package.md)。

## 成功标准

目标包、执行入口、触发方式和认证绑定的配置读回一致；未验证的运行条件明确列出。若无法读回平台侧配置，保持 partial，不把本地 workflow 写完当作链路完成。

## 坑与恢复

没有本机登录不等于 OIDC 失败。没有 NPM_TOKEN 不等于 CI 未配置。信任对象或环境不匹配时修正准确字段，不增加长期 Token 来掩盖未定位的问题。凭据只进入用户选择的专用存储。

## 证据与边界

2026-10-15 官方文档指导，尚未配置真实账户或 workflow。配置与发布各自留证；按[写回协议](../../../knowledge-schema.md)维护。
