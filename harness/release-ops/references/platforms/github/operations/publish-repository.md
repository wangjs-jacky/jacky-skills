# 首次发布仓库

## 目标

将当前工程发布到用户指定的 GitHub 仓库及分支，保留现有代码与项目约定。

## 前置条件与授权

已明确 owner、仓库名、可见性、源码范围与目标分支；不能由“发布”推断为公开。先读[平台档案](../index.md)，核对当前 git 状态、remote 和有效 GitHub 身份，仅输出必要身份结论。

## 流程与检查点

1. 确认是否已有目标仓库或 remote；已有时转[推送改动](push-changes.md)，不重复创建。
2. 检查将提交的具体文件和项目忽略规则，保留无关改动。README/About 只按本次需要准备，不重写现有文档或强制生成多语言版本。
3. 用当前 `gh repo create --help` 确认参数，显式指定目标、可见性和 source/remote；避免连带推送未核对的本地提交。
4. 若创建与推送分开执行，逐项记录结果；用精确 ref 推送已确认提交。
5. 读回仓库身份、可见性和远端目标分支，关联预期源码提交。

## 成功标准

目标仓库存在且身份/可见性正确，指定分支包含预期提交；任务要求的项目信息已写入。只创建空仓库不满足包含源码的发布目标。

## 坑与恢复

命令失败先检查仓库是否已创建、推送是否已到达。名字冲突先核对目标身份，不自动删除仓库或改名。原始运行日志的尾部空行应按数据原样保留；源代码与文档的空白检查可用明确路径排除证据目录，不能为让检查通过而修改已冻结证据。连通性问题不修改无关全局配置；已有仓库进入适用操作继续。

## 证据与边界

基于 2026-10-15 官方 CLI 文档与迁移后的设计规则。2026-10-18首次真实场景已核对目标不存在、有效CLI身份和明确公开授权；将已审阅的静态报告与demo精确提交，用gh repo create显式目标/public/source/remote/push发布，API读回仓库visibility、homepage及main提交一致。随后验证说明提交也已推送并读回，工作树干净。具体项目和提交归本机实例；这不代表GitHub Pages、Release或自动CI已经配置。
