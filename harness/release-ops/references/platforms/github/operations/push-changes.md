# 推送指定改动

## 目标

将本次授权的提交推送到明确的仓库和分支。

## 前置条件与授权

读[平台档案](../index.md)。核对目标 remote、当前分支、工作树、已有本地提交和远端关系；不能把同一目录中的无关改动或之前提交一起发布。

## 流程与检查点

1. 区分本次文件、已暂存内容、已有提交及远端差异。目标是部分改动时采用精确暂存或从正确远端基点建立隔离 worktree；README、manifest 等共享文件还要按具体差异核对，不能仅因文件在清单内就带上其中无关的未发布内容。
2. 按项目版本约定处理本次变更；提交后核对实际 diff 和预期提交。已有合适提交直接复用。
3. 明确推送 ref 和分支策略；需要 PR 时推到工作分支并创建指向正确 base 的 PR，不自动合并。用户已授权合并则继续[合并 PR](merge-pr.md)。
4. 使用精确目标执行常规 push，记录其结果。PR 正文等多行内容用文件参数传入，避免 shell 展开。
5. 读回远端分支 SHA，必要时确认预期提交的祖先关系；远端被并发推进时核实差异，不自动覆盖。

## 成功标准

正确远端分支已包含本次预期提交，且提交范围与授权一致。若还要求 PR，则 PR 的 base/head 和改动范围也已核对。推送成功不代表已合并或已发布包。

## 坑与恢复

非 fast-forward 时检查两端差异，不默认 force push。网络失败先单次核对远端是否收到提交；不要重新提交同一改动或清空工作树。目标仓库的 CI 结果与本次提交对应，不能借用旧提交绿色状态。

## 证据与边界

2026-10-15：从最新远端主分支建立隔离 worktree，精确整理 77 个授权共享文件，提交并常规推送到工作分支；读回远端 SHA 与本地提交一致。随后创建 PR，核对 base、head SHA 及全部文件范围，原脏工作区其他文件保持不变。

验证范围为普通分支推送及 PR 创建，不包括 force push、受限凭据或网络结果不确定的恢复分支。真实仓库、分支、提交与 PR 证据存私有实例；按[写回协议](../../../knowledge-schema.md)维护状态。
