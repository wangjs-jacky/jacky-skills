# 定位外部加载瓶颈

## 目标与前置条件

定位首次打开/刷新慢发生在响应、传输、执行还是业务恢复。确认同一版本与真实外部客户端，CLI请求只作为对应段的对照。

## 执行判断

记录Navigation Timing的首响应、DOM和load，以及Resource Timing的持续时间、transferSize和decodedBodySize。按耗时和传输量定位资源，再普通刷新与新标签打开各取一次对照；不用固定时钟反复查询状态。

从源站读取同一资源并对比缓存/压缩头；经过网关的差异与CDN状态单独核对。保留浏览器实际可见及API/连接证据，避免只看到暂态壳就声称就绪。

## 成功标准

主要等待与资源已定位，同资源本机/外部以及首次/再次加载有可比证据；结论明确区分已确认与待查。诊断不等于整改完成。

## 坑与恢复

本机毫秒级而跨网秒级不表示客户端算力不足；压缩已存在时不能再把“开启压缩”当新方案。缓存后transferSize为0可证明复用，整页仍可能因HTML首响应或业务恢复慢而波动。

## 证据边界

2026-11-08，实体外部电脑首次与刷新显示压缩后约4MB合并前端包重复下载，同资源源站读取毫秒级，网关覆盖原生缓存头已确认。来源是单一应用运行/源码证据，未泛化为所有网页或所有客户端性能。

2026-11-09第二案例：Next源站已有gzip与版本资源immutable，网关覆盖no-store导致外部浏览器主脚本重复约2.1MB传输、刷新load约36.7秒；受限私有缓存后同客户端刷新约2.27秒、28项版本静态资源0传输。大型插件元数据仍需十几秒，确认静态下载与业务恢复是两个瓶颈，未把缓存命中后的导航当作冷加载。
