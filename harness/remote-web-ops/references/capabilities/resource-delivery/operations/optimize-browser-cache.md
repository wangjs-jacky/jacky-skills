# 优化浏览器资源缓存

## 目标与前置条件

让外部浏览器复用可缓存的版本静态资源，同时保留当前应用身份和数据边界。先完成diagnose-loading，确认内容是否用户相关、版本URL是否对应不可变内容、旧版本请求如何处理。

## 执行判断

把原生响应、网关响应和浏览器命中逐段对照，确认是原有策略被覆盖还是源站没有声明。没有Cache-Control不等于没有缓存限制；同时检查Expires/Date、Pragma及其他实际约束。

选择缓存范围和TTL时保留上游更短有效期及显式限制。无法证明某条规则安全适用时保持保守策略；版本标识的存在需要内容更新语义支撑，不能仅凭文件名看起来像hash。

对受保护应用优先评估浏览器private缓存；共享CDN缓存需独立确认内容和身份边界。本案例的HTML、API、私有文件和错误响应保持no-store，不作为所有公开网页的普遍策略。

改动前保留定点回退，先写会暴露误缓存的真实HTTP回归，再最小修改；真实资源GET/HEAD、错误/旧版本、方法/类型、登录/退出及相关实时连接分别验收。具体缓存指令与资源匹配属于应用适配，不复制到其他服务。

## 成功标准

同版本普通刷新和再次打开不再无谓重传目标资源；版本机制、权限、错误响应与私有内容仍符合应用约定。真实升级未执行时明确说明只验证了源码版本语义和错误版本拒绝，不能冒充发布升级验收。

## 坑与恢复

- 只修插件组合包可能漏掉打包主脚本/CSS；按浏览器证据逐类核对，不能一口气放开整站。
- 无CC时直接给一天immutable可能覆盖Expires/Pragma限制；本案例补失败回归后选择保守no-store，其他服务也可按其语义精确计算剩余有效期。
- static程序已下载不因注销远程消失；注销后的私有API和网络访问仍须被拒绝。
- 回退只恢复本次策略并加载，不清空数据库、重置代理或覆盖后续并行改动。

- 某些Next侧车的未知静态URL会回退成HTML200并带共享缓存指令；只看路径和200不足以放行，须同时检查响应MIME及原生版本资源契约。

## 证据边界

2026-11-08，单一应用版本资源从网关no-store改为受限private策略；普通刷新/再次打开主要资源transferSize为0，真实权限/API/WS及注销回归通过。私有TTL上限一天是该案例选择，非本Skill默认。50项自动测试、类型检查和17项真实协议已在原目标留证，Expires/Pragma缺陷经独立审查后先红后绿修复。首次未缓存下载、长稳和跨应用适配未证明改善。

2026-11-09第二案例：另一Next应用的网关静态私有缓存、权限/项目SSE及退出协议通过，未知chunk回退HTML被保守拒绝缓存。外部Mac普通刷新load约36.7秒降为2.27秒，新标签约2.36秒，28项Next资源transferSize均为0，真实首页及既有项目预览可见。已有浏览器缓存，未证明冷加载改善；大插件目录接口仍15–19秒，模型可选与load分别验收。没有真实升级或长期稳定性结论。
