## 步骤与检查点

1. 对齐机器/容器身份、进程树、会话 ledger、活跃 turn/排队/审批与恢复能力。
2. 区分整机睡眠、网络、电源、内存与 daemon 心跳；缺日志不指定唯一根因。对照实际进程树与 daemon 登记，记录运行版本混用；登记不覆盖全部旧 worker。
3. 逐个扫描完整日志中 anchored 的最后 turn/thinking 生命周期事件，再看日志静默时间与后代集合。近期日志可能只是 Socket 重连或技能通知，不等于业务 turn 活跃；缺日志和未知后代单独保留。区分 top MEM、压缩、swap 与 ps RSS，不能相加预测回收收益。
4. 回收、容器替换或防休眠调整只在授权内执行，保留未知进程；使用不会拉起被测服务的观察。授权针对已审核候选时，不自动扩大到新近静默会话。
5. 生成本轮进程身份快照，逐个发送正常退出信号前复查启动时间、精确命令、日志终态/静默及完整后代集合；变化则跳过。保护当前执行祖先，旧 PID 名单只能审计，不能复用执行。
6. 正常退出后单次核对目标全树退出、保留 worker 身份仍匹配和 daemon 控制 API，记录实际资源快照。控制 API 的瞬时超时与目标退出分开记录，不因此直接重启服务。

## 成功标准

目标全树退出、保留进程身份匹配、本地控制 API 可用，目标资源变更可观测；清理成效与瞬时采样分开。若声称业务可继续或恢复成功，还须另有对应真实会话证据。

## 失败模式与恢复

PPID=1 或 daemon 无登记不证明闲置；RSS 相加不等于实际释放。Compose init 配置不证明旧容器已重建，不能让两个活跃实例共用身份目录。
