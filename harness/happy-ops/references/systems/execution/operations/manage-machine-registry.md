# 核对与清理设备记录

- system: execution
- operation: manage-machine-registry
- status: verified
- last_verified: 2026-10-24
- risk: medium
- scope: 同一账号的设备身份核对、离线临时测试设备删除、明确授权的专用设备daemon及relay自启停用、设备删除及404读回、保留会话API和进程身份核对；不含业务迁移、既有worker终止、未识别设备删除或UI浏览器验收。

## 目标

区分同一物理主机上的主执行端、专用后台与测试残留，清理已确认无用途的设备记录。

## 前置条件与授权

用户已授权目标设备清理；先只读核实身份与依赖。凭据仅通过应用既有授权在内存中使用，不输出或保存。专用服务影响超出历史残留清理时，明确影响并取得相应选择。

## 入口

先读[执行端系统索引](../index.md)，需要本机证据时读[私有操作入口](../../../../local/systems/execution/operations/manage-machine-registry.md)。按当前服务源码核对删除语义及客户端删除事件处理。

## 步骤与检查点

1. 获取设备列表，把精确machineId与可解密metadata、HAPPY_HOME_DIR/settings、daemon.state、launchd入口和业务配置关联。主机名相同不能证明记录可删；目录隔离会产生独立设备身份。
2. 对照本机控制API的会话登记和服务配置，辨别专用后台。登记数量不等于活跃模型turn数量；在线与离线只是判断输入，不能单凭离线删掉未知设备。
3. 明确授权停用专用后台时，先以launchd标签核对关联入口，保存需保留进程的启动时间与命令身份。持续禁用自动启动，再卸载目标后台；核对停止语义及分离进程组，避免把停止daemon扩大为终止普通聊天worker。确认daemon真实退出，且launchd目标未加载、disabled覆盖已生效。
4. 删除前重新GET精确machineId，检查预期metadata、离线状态或已停止的真实后台及用途。使用现有账号隔离API，不直接改数据库。
5. 删除后单次读回404及完整列表，核对保留daemon存活、必要控制API可用。只有操作过浏览器才声明页面实测。
6. 隔离联调收尾分别核对worker、daemon、账号绑定、临时目录与服务端机器记录，不能把停止daemon或删除临时目录当成设备记录已清理。

## 成功标准

指定废弃设备已删除且读取404，保留设备仍存在，必要执行端控制接口可用；未识别设备和仍有业务依赖的专用后台保持原状或按另行确定的影响范围处理。

## 失败模式与恢复

强行让两个活跃daemon共用machineId可能争用RPC和连接。删除仍运行的专用设备会使业务调用失效，并可能在其重启后重新注册。不能通过删记录、换名或只停心跳宣称服务已合并；业务配置与加密密钥解析可能仍绑定旧身份。
