# Cloudflare 无轮询链路审查

在设计、修改或排查现有服务时读取。约束原文归 [Skill 入口](../SKILL.md#用户约束禁止-cloudflare-轮询)；本文件说明如何检查真实行为。

## 找到每一跳的数据来源

沿页面 → Worker → DO → 执行桥接/SDK → 回调/消息 → 页面，标记：谁修改状态、谁发事件、谁订阅、谁读取存储、何时重试、哪个函数再次安排执行。用源码调用链与实际事件证据共同判断。

可以用 `rg` 初筛 `setInterval`、`setTimeout`、`sleep`、`alarm`、`scheduled`、`Cron`、`watch`、`poll`、`refetchInterval`、`refreshInterval` 和 `retry`，再查看调用方与 SDK 配置。关键词不是结论：名为 poll 的一次调用未必是轮询，名为 stream 的接口也可能在内部循环查状态。

## 按服务状态检查

| 状态 | 合规事件来源 | 必查问题 |
| --- | --- | --- |
| 空闲 | 入队/状态提交时通知订阅者 | 是否周期 claim、扫表、查 schema 或取 usage |
| 执行中 | 执行器进度/完成/失败事件或回调 | SDK watch、进度 API 和 SSE 生产者是否周期查询 |
| 完成/取消 | 单次终态写入和通知，幂等消费 | 是否残留定时器、监听器或完成后查询 |
| 断线/重连 | 连接事件触发一次快照或游标补齐 | 是否把断线重试设计成不断“连上→查状态→关闭” |
| 冷启动/休眠恢复 | 构造恢复、连接 attachments、幂等迁移 | 是否反复扫描历史重建状态或依赖丢失的内存 |
| 运维查询 | 已有告警/事件或用户动作触发单次读取 | 是否用 cron/sleep 循环监测“修好没有” |

单次 deadline 用来结束操作，可以保留；deadline 结束后自动查状态并安排下一个 deadline 就是轮询。网络重连可做纯连接恢复，但不得把业务查询藏进无限重连循环。保活只用于连接健康，不能读写存储、扫描或取进度。

## 处理与证据

1. 在用户已授权的代码范围内，把反复查询替换为真正的生产者事件/订阅/回调。需要单次对账时明确触发来源及次数。
2. 若上游没有事件能力，明确记录不能自动获知的状态与影响；可采用用户单次刷新或改造回调接口，不自行增加轮询兼容层。
3. 对相关状态逐一记录源码位置、触发条件、SDK 实际行为，以及已有的请求/消息/SQL 证据。静态搜索无命中不是运行证明；一段时间无请求也不证明执行中路径无轮询。
4. 若用户请求运行验证，采用事件订阅、已有日志和有明确起止的单次操作，核对保活零业务访问、幂等、取消、断线及冷启动。不要另写一个循环查询器做验证。
5. 明确列出已移除、仍存在和无法核实的路径；只有全部相关路径满足约束，才能宣称该服务无轮询。

仅维护知识的任务，把已知残余写入私有实例与相应 operation 的证据边界，不擅自扩展到修改/部署应用。
