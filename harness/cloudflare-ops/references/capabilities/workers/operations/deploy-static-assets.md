# 发布静态文件并核对分发结果

## 目标

将已有公开静态成品部署为独立Workers Static Assets，核对活动版本和关键文件字节。浏览器交互与各地区连通性分别记录，不由CLI或HTTP文件验证自动推断。

## 适用状态与前置条件

用户明确授权Cloudflare长期部署；已确认账号、工具认证、全新Worker名称和公开目录。复用已有成品，私有输入、认证与无关工程不进入资源目录。若同名Worker已存在，先核对归属与配置，不直接覆盖。

## 设计与执行

1. 从项目锁文件使用本地Wrangler；新工程安装并锁定实际版本。通过whoami核对认证和单个账号，只记录身份与权限结论，不打印或复制凭据。新版CLI可能使用加密配置，优先让CLI消费原有认证，不把缺少旧toml文件视为未登录。
2. 配置assets.directory与明确Worker名、当前compatibility_date；纯静态实现可不提供main与ASSETS binding。资源目录独立于源码与node_modules，部署时记录实际资源清单。
3. 执行项目dry-run，再一次部署；结果不明确时单次读回，不创建任务状态查询循环。部署与事件脚本不引入Cron、Alarm、轮询或状态扫描。
4. 一次读回活动部署，核对预期版本的流量比例。GET网页、下载包和报告等关键业务文件，比较字节或SHA-256及适用的Content-Type/下载头；仅首页200不够。
5. 若使用浏览器，遵循ego-ops/Ego控制权与截图证据规则。某条终端路径成功不证明浏览器或其他网络能连接；浏览器失败单列，不能复用先前临时预览图片冒充本次成功。

## 坑与恢复

新Worker检查返回不存在可作为创建前证据，不等于部署失败。代理与直连结果不同只记录路径和观察，不据此宣称根因已确认。CLI版本与本机认证格式、HTTP成功与浏览器可读须分别核对，不修改全局代理或擅自占用既有域名来规避失败。

## 成功标准

账号与新目标明确，部署成功且活动版本读回匹配；关键公开文件与原件字节一致，必要下载头正确；公开资源与业务轮询范围已检查。其他浏览器、地区、长期稳定性或自定义域名未验证时保留明确限制，不计作本条已验证范围。
