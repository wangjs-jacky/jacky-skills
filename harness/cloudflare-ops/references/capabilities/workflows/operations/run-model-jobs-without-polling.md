# 执行有外部模型副作用的耐久任务

## 目标

在不查询循环、不依赖浏览器连接的前提下执行有限任务，并明确重复调用、取消和结果不确定时的恢复。

## 适用状态与前置条件

已确定业务状态所有者、输入修订、模型调用方式和用量来源。模型自身幂等/取回/取消能力未验证时，不将其作为可靠性前提。平台默认值见[能力档案](../index.md)。

## 设计与执行

1. 在业务事务内保存job/attempt、预算、确定性workflowId及dispatch intent，事务外创建Workflow。创建结果模糊时不换ID自动重发。
2. 每个外部callId在事务内只授予一次发送许可。步骤重新进入也必须重新领取，已claimed就不再发请求；不能把可重放的步骤返回值当发送许可。
3. 明确配置重试策略；业务失败可用NonRetryableError。拟设零重试时仍应在锁定版本验证，不能用配置取代持久副作用记录。
4. 收到明确上游终态后先保存大产物，再以输入版本、attempt和取消栅栏校验提交结果；只把小引用返回检查点。
5. 事务提交状态和事件后再广播。通知失败不重做模型；入队与终态事件推动一次调度。SDK自身重试、自动重连与watch实现必须一起审查。
6. 模糊态通过用户动作单次读取固定workflowId与产物。已有结果可补提交；无结果而可能已调用时保留unknown，只有用户明确接受重复成本才创建新attempt。
7. 取消先持久增加栅栏，再单次terminate/abort。旧结果不得发布，usage可补账；不保证上游立即停算或不收费。

## 坑与恢复

DO事务不能同时提交Workflow创建、R2写入与外部模型请求。发送许可后、fetch前的崩溃也必须按不确定处理，可能需要人工恢复。删除/导出应与模型槽分开，不能因未知推理阻止用户管理资料。不能用周期Alarm、Cron或sleep查询补偿丢事件。

## 成功标准

在发送许可后、外呼完成后、产物落盘后、状态提交后分别故障注入；恢复不得自动产生重复模型请求。取消与完成竞态、旧修订拒绝发布、未知usage保留、断线单次恢复、空闲和运行中无轮询均有真实证据。
