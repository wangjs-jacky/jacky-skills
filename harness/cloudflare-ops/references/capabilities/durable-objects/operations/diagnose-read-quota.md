# 从读取告警定位应用与调用源

## 目标

明确告警计量项、账户与时间窗，定位主要消费 namespace、所属应用和造成读取放大的调用路径，形成可执行的止损与整改对象。

## 适用状态与前置条件

出现 DO 读取额度告警或存储操作因额度失败。先读[额度与超限行为](../index.md#限制与额度)。截图是定位线索，不能据告警邮件的账户级标题直接推断应用。

## 设计与执行

1. 确认告警针对 rows read、rows written、容量、请求还是时长；区分接近限额与已经耗尽。固定 UTC 时间窗和账户，不混用不同日期的计数。
2. 对当前可用 analytics/API 做单次聚合读取，按 namespace 等受支持维度定位主要来源；核对脚本 bindings 与 class 映射。接口权限/粒度不足时报告缺口，不将空结果解释为零消耗。
3. 关联发布版本、生产者与日志，查看空闲领取、schema 初始化、历史扫描、进度同步和重连路径。别把所有读取都归咎于一条 SQL；可能同时存在高调用频率和单次扫描放大。
4. 必要时对代表性 SQL 单次测量 `rowsRead/rowsWritten`，cursor 消费完成后取值；选择不改变生产业务状态的路径。估算“每次实际行数 × 事件/调用量”，注明样本与误差。
5. 将具体来源、证据、止损对象与影响范围写入私有实例。若用户已授权先停服务，停止已定位的生产者/触发器并单次核对；共享 namespace 或账户不能无依据全部停掉。待对象唯一、影响明确后再执行。
6. 转入[减少读取放大](reduce-read-amplification.md)。故障根因与恢复分别结论：停止新增消耗不会补回已经耗尽的日额度。

## 坑与恢复

- Analytics 的窗口、延迟和权限会影响结果；空数据不等于无请求，需要结合源码、当前绑定和业务错误。
- 返回空任务仍可能扫描大量历史行；仅查看结果数量会漏掉成本。
- 本地进程停止后可能被服务管理器自动拉起；检查其已知启动方式与当前状态，不实现循环检查。
- 账户中其他应用也共用额度；主要来源被停止不代表总读取必然归零。

## 成功标准

有同一时间窗内的告警/用量依据、namespace 到应用的映射、主要调用源和源码或实际计量证据，能明确止损与整改目标。若只能猜到应用，保持 `partial`。本操作的成功是完成诊断，应用整改和业务恢复另行验证。

## 验证证据与边界

2026-10-14 的实际会话通过账户用量分解、绑定映射和源码检查，定位某应用约占读取的 96%；桥接空闲领取频率为约 1.5 秒一次，叠加 schema 与历史任务扫描。已停止具体生产者并核对，满足本操作诊断目标。完整实例映射与原始证据仅保留在 ignored 应用记录。

该证据不支持“所有轮询已移除”或“账户当天额度已恢复”；后续修复仅部分验证，见[整改边界](reduce-read-amplification.md#验证证据与边界)。复用此经验时必须重新核对当前时间窗、绑定和调用源。
