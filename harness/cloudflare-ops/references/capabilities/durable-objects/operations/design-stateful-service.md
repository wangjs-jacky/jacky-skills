# 设计状态与事件服务

## 目标

围绕真实业务场景明确 DO 身份、状态、事件和恢复方式，在平台额度内完成事件驱动设计。

## 适用状态与前置条件

新建或重构任务协调、会话状态或通知服务；已知读写方、事件来源、并发需求和持久化边界。先读[能力档案](../index.md)，确认账户套餐和后端；不知道的负载参数标为待测，不编造容量结论。

## 设计与执行

1. 按协作边界选择 object key，明确状态唯一所有者、访问授权和共享范围；避免所有用户都落进单对象，也避免拆分破坏必要的一致性。
2. 列出事件与状态转移：创建/入队 → 通知执行者 → 领取 → 推送进度 → 完成/失败/取消。定义序号、幂等键和重复事件处理，不通过定时扫描发现状态变化。
3. 确认每一跳确有可用事件接口。SDK 名为 watch/stream 仍需检查实现；没有事件能力时采用回调、真正的订阅或用户单次同步，并说明能力缺口，不静默降级成轮询。
4. 通知与领取之间防丢事件、重复领取和竞争；持久化结果与发送通知的失败窗口要有明确恢复办法。单次连接建立可读取一次快照/游标差量；不能靠不断重连再查状态模拟订阅。
5. 若 DO 接收 WebSocket，评估 Hibernation API。使用可恢复的连接 attachments/持久状态，构造函数保持轻量且幂等；普通内存缓存不能替代冷启动恢复。
6. 用事件量、每事件查询读写行数、连接/重连次数、对象活跃时长估算账户消耗，给其他应用和恢复操作留余量。无需等待额度告警才测量热查询。
7. 依[事件链路审查](../../../event-driven-review.md)覆盖空闲、执行、结束和断线场景；持续运维采用现有事件/告警或人工单次查询。

## 坑与恢复

- 前端 WebSocket、服务端轮询数据库：传输方式没有解决事件来源，需从状态提交处产生通知。
- 休眠后内存丢失：从持久状态与连接 attachments 恢复，不能依赖前一个进程的数组或布尔变量。
- 为处理丢事件新增周期 Alarm：恢复仍须符合用户禁止轮询规则；采用明确事件或人工单次恢复，并暴露未解决的投递保证。
- 无索引的“只取一条待执行任务”：实际读取仍可能随历史增长，应测 cursor 消耗而非响应大小。

## 成功标准

设计说明能逐一指出每个状态的生产者、事件、持久化归属、幂等与恢复策略；额度估算引用能力档案并注明假设；实现后以实际事件与存储计量证明，才能将该场景标为已验证。
