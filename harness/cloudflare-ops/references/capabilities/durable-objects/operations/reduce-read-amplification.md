# 消除轮询与读取放大

## 目标

移除目标服务完整链路中的业务轮询，降低必要事件触发查询的读写成本，并保留任务、状态和通知语义。

## 适用状态与前置条件

已按[读取诊断](diagnose-read-quota.md)定位生产者、热查询和绑定；有可读回状态及兼容迁移方案。设计前读[DO 能力限制](../index.md)，禁止用升套餐、延长间隔或退避代替用户要求的去轮询。

## 设计与执行

1. 先画出页面 → Worker → DO → 执行桥接/SDK → 完成/进度回调的真实调用链；按[事件审查](../../../event-driven-review.md)标出周期数据读取。
2. 在入队或状态提交处产生事件。执行者订阅可休眠的 DO 服务端 WebSocket 等真实通知；收到事件才领取任务。建立连接时可以做一次同步以弥补断线缺口，不把空队列当循环重试条件。
3. 将重复 schema 检查移出热请求路径，采用幂等迁移与适当的内存缓存；缓存失效/冷启动必须正确，不能靠永不重启假设跳过必要恢复。
4. 根据实际过滤与排序创建索引，缩小任务、事件和游标查询范围。比较完整 cursor 的读写行数；索引写放大也应计入，避免为省读无限增加写入。
5. 进度与完成由生产者事件或 SDK 的真实订阅推送；SSE 服务端不定时读库。去掉执行中 watch/progress 的周期查询；底层无事件接口时报告缺口，选择回调/用户单次同步等可行方式。
6. 移除循环扫描用途的 Alarm/Cron。协议或自动保活不访问业务状态/存储；连接在空闲时应具备实际休眠条件。
7. 按真实事件观察通知、领取、进度、完成、取消、重复投递与断线恢复，核对数据保留及查询消耗。记录运行样本与未覆盖路径，不能创建周期查询监测器来“证明无轮询”。

## 坑与恢复

- 仅停空闲 claim：执行中的轮询仍在，应明确列为未完成路径。
- 无任务响应很小：可能仍发生 schema/全表扫描，应看真实 SQL 行数。
- 缓存 schema 后首次冷启动变慢或不正确：核对迁移幂等与构造路径。
- 上层转为 SSE 但下层 SDK 仍在 sleep+query：需要改变事件来源。若暂时做不到，记录能力缺口，不自动恢复旧轮询。
- 代码已修但当天仍报 quota 错误：按能力档案的重置规则判断；不要重复压测或用循环重试继续消耗。

## 成功标准

相关路径的空闲、执行、结束/取消、重连和冷启动均无业务轮询；必要查询的读取成本有实际证据；任务语义、持久状态、绑定和部署读回正确。运行证据缺少的部分保持待验证。

## 验证证据与边界

2026-10-14 案例已验证：移除空闲领取轮询；加入通知连接、schema 缓存和查询索引；事件驱动的进度传输；移除周期扫描 Alarm；保活零 SQL 读取；既有状态与部署绑定保留。
